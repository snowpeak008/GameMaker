## 0. 核心主张与愿景保真对照

**核心主张一句话**：把设计空间的第一等公民从"决策点"换成"系统"——玩法 = 从系统库实例化若干系统，每个实例带一个五维重度档，实例间以名词端口连接，组合合法性由三条可机器校验的规则（重核形态 / 重度预算 / 重度传导）判定；决策点降级为系统模块内部的机制选择器，由重度档而非解锁瀑布驱动激活。

## 1. 系统本体模型（Q1）

### 1.1 什么是一个系统：定义与边界三测试

**定义**：一个系统 = 一组机制规则 + 这组规则独占写权限的状态（数据表/状态机）+ 对外的名词端口。系统是"状态所有权 + 规则闭包"的单位，不是功能菜单上的一个页签，也不是体验层的一个主题词。

**边界三测试**（判定"X 算不算一个独立系统"，两个不同评定者应得出相同结论）：

- **T1 状态所有权测试**：存在至少一张只有该候选系统能写的数据表或状态集。其他系统只能通过端口读它，或通过修饰器（modifier）经它自己的规则改它。没有独占状态的，不是系统（是另一个系统的机制，或是一个纯标签）。
- **T2 可摘除测试**：把候选系统整体摘除，只允许删接口边、不允许改写任何其他系统的内部规则，游戏其余部分仍是可运行的（可能变无聊，但规则自洽）。若摘除 X 必然迫使 Y 的内部规则改写，则 X 和 Y 是同一个系统。
- **T3 名词转换测试**：系统必须至少消费一个名词并产出或修饰至少一个名词（见 §1.2 名词分类）。只存数据不转换任何名词的（如一张纯配置表），是某系统的数据资产，不是系统。

**判例 1（简报 Q1 原题）：装备 / 宠物 / 背包是三个系统还是一个"成长系统"的三面？**
答：三个系统。T1：装备表、宠物表、背包格各有独占写权限的状态；T2：摘除宠物系统，装备与背包规则一字不改仍自洽（反之亦然）；T3：三者各有独立的名词转换（装备消费装备实体、修饰战斗属性；宠物消费宠物实体、修饰或参与战斗；背包消费一切实体、提供存取事件）。"成长"是 Dynamics 层的聚类标签（这三个系统都产生"成长感"动态），不是系统——**用 MDA 的 D 层词汇给系统命名是本模型明令禁止的**，因为 D 层词没有状态所有权，无法通过 T1。

**判例 2（反例）**："手感系统"不是系统——没有独占状态表（T1 不过），它是战斗/移动系统 L4 参数的品质属性。"新手引导"是系统——有独占状态（引导进度表）、消费事件（玩家首次行为）、产出修饰器（UI 高亮/功能锁）。

### 1.2 系统接口规范：四类名词 × 三类端口

系统间只允许通过**名词端口**交互。名词四类：

| 名词类 | 定义 | 判定 | 例 |
|---|---|---|---|
| 资源 resource | 可计数、可增减、可转移的量 | 有余额语义 | 金币、体力、能量、行动点 |
| 实体 entity | 有属性表的对象实例 | 有行标识 + 属性列 | 一件装备、一只宠物、一张卡、一个敌人 |
| 事件 event | 时点信号，带载荷 | 有发生时刻，无余额 | 击杀、升级、波次结束、回合开始 |
| 修饰器 modifier | 作用于其他系统属性或规则的持续效果 | 有作用目标 + 生效期 + 叠加序 | 套装加成、遗物效果、buff |

端口三类：**provides**（产出名词）、**consumes**（消费名词）、**modifies**（向其他系统挂修饰器）。一条接口边 = （源系统, 端口, 名词, 目标系统）。系统实例图 = 系统为节点、接口边为边的有向图。这张图是 §3 组合校验器的输入。

**判定标准**：一个系统的接口声明是否完整，检查法为——遍历其所有 L4 机制的 `effects_template`，凡引用非本系统所有的实体/资源/属性，必须存在对应接口边；无边即校验失败（这就是审计 B 里"探针列静默放行"问题的堵法：跨系统引用必须过端口）。

### 1.3 MDA 映射规范

每个系统模块强制填三层（不再是现行 `mda_layer` 那种可选展示标签）：

- **M（Mechanics）**：本系统的 L4 决策点列表——这层就是现有 pack 窄链，原样保留。
- **D（Dynamics）**：本系统预期产生的运行时动态，用"谓词 + 可观测信号"写，禁止形容词。合格样例："玩家在获得新装备后 30 秒内打开装备界面比较词条"（可观测）；不合格样例："产生成长的爽快感"（不可证伪，属 A 层且写错了位置）。
- **A（Aesthetics）**：服务 MDA 八分类中的哪几类（感官/幻想/叙事/挑战/社交/探索/表达/消遣），限选 ≤2 个主项。

映射的用途是校验而非装饰：组合模板层面，所有 core 系统的 A 层主项并集 = 该玩法的美感承诺；若某系统的 A 主项与玩法承诺完全不相交且 κ=core（见 §3.1），校验器出警告（"核心系统服务的美感与玩法承诺脱节"）。

## 2. 重度模型（Q2）

### 2.1 五维量表：全部可数，两人同判

重度 W(S) = M + D + C + P + O，五维各 0-3 档，总分 0-15。档位映射：**轻 0-4 / 中 5-8 / 重 9-12 / 极重 13-15**。

| 维 | 名称 | 数什么 | 0 档 | 1 档 | 2 档 | 3 档 |
|---|---|---|---|---|---|---|
| M | 机制深度 | 系统内 L4 级独立机制规则数（一条规则 = 一个可单独启停的 `effects_template` 组） | ≤1 | 2-3 | 4-6 | ≥7 |
| D | 数据深度 | 系统独占的数据结构数（表/矩阵/曲线/图各算 1） | ≤1 张简单表 | 2-3 | 4-6，或含矩阵 | ≥7，或含图/嵌套结构 |
| C | 耦合宽度 | 系统实例图上以本系统为端点的接口边数 | ≤1 | 2-3 | 4-6 | ≥7 |
| P | 决策形态 | 玩家在本系统内的决策结构（四选一判定，见下） | 无决策（纯被动） | 偶发一次性选择 | 会话级重复决策 | 构筑级组合决策（选择空间相乘） |
| O | 内容供给 | 上线所需内容行数量级（该系统所有表的行数合计） | ≤10 | 11-100 | 101-1000 | >1000 或需持续运营供给 |

**可复现性论证**：M 数机制条目、D 数表、C 数边、O 查基数期望（`cardinality_expectations` 已有此机制）——四维是纯计数，对同一份系统模块文档两个评定者必然同分。P 是唯一含判断的维度，给判定问句消歧："玩家的两次选择是否互相组合出新价值？"是→3；"玩家是否每个会话都重复面对该选择？"是→2；"选完是否长期不再碰？"是→1；"玩家是否根本没有选项？"是→0。仍有分歧时取证据：录一段真实玩家会话，数该系统的决策触点。

**量表的刻意取舍**：五维等权、粗档位。等权是初标定（无回归数据支持加权），粗档位是为了评定鲁棒——差一个机制不改变档位结论。代价见 §2.4 已知局限。

### 2.2 装备系统全谱系标定（第一标定样例）

每档写明：新增子机制（累计计数）、新增数据表（累计）、新增接口边（累计）、五维打分算式。

**E0 纯属性加成** —— 轻，W=3
- 子机制：①穿戴槽位规则（每槽一件，穿上即加属性）。累计 1 条 → M=0。
- 数据表：装备表（id/槽位/属性加成列）。累计 1 → D=0。
- 接口边：consumes 装备实体（来自掉落或商店）；modifies 战斗系统属性。累计 2 → C=1。
- 玩家决策：数值比大小换装，偶发 → P=1。内容：数十件 → O=1。
- **W = 0+0+1+1+1 = 3（轻）**

**E1 + 品质与随机词条（属性 BD）** —— 中，W=7
- 新增子机制：②品质分层规则 ③词条随机生成（词条池 + 条数按品质）。累计 3 → M=1。
- 新增表：品质表、词条池表。累计 3 → D=1。
- 新增边：modifies 掉落系统的生成规则（品质权重）。累计 3 → C=1。
- 决策升级为会话级词条取舍 → P=2。内容：词条 × 品质组合，101-1000 → O=2。
- **W = 1+1+1+2+2 = 7（中）**

**E2 + 技能 BD（装备携带触发/主动技能）** —— 重，W=11
- 新增子机制：④技能触发条件规则 ⑤技能效果绑定规则。累计 5 → M=2。
- 新增表：装备技能表（触发条件/效果引用）。累计 4 → D=2。
- 新增边：provides 修饰器给技能系统；consumes 技能系统的效果定义。累计 5 → C=2。
- 词条 × 技能联动，选择空间相乘 → P=3。O=2。
- **W = 2+2+2+3+2 = 11（重）**。谱系拐点在此：E1→E2 是"数值比较"到"构筑组合"的相变，P 从 2 跳 3。

**E3 + 宝石镶嵌** —— 重，W=12
- 新增子机制：⑥孔位生成规则 ⑦镶嵌/拆卸规则。累计 7 → M=3。

## 3. 组合规则（Q3）

### 3.1 核心循环与关联强度 κ

**核心循环**：L2 层声明的最小可玩闭环，写成动词序列（如幸存者："移动→自动攻击→拾取经验→三选一升级→移动"）。核心循环是组合结构的锚，没有它 κ 无从判定——所以 L2 新增一个必填决策点：`core_loop`（动词序列，每个动词必须绑定到一个系统实例）。

**关联强度 κ(S) ∈ {core, strong, weak, meta}**，判定标准（按序适用，取首个命中）：

| κ | 判定 | 例（幸存者） |
|---|---|---|
| core | 系统的机制出现在核心循环动词序列内 | 即时战斗、局内构筑 |
| strong | 系统 provides 核心循环消费的名词，或 modifies core 系统属性，且每局必然触达 | 波次遭遇、掉落 |
| weak | 可绕开或影响间接（摘除后核心循环仍完整转动） | 成就图鉴 |
| meta | 只在局外生效 | 局外解锁 |

### 3.2 R-C1 重核形态规则

"一个重度核心 + 若干轻度辅助"形式化为**合法形态枚举**（按 L0 项目档案的产品档位选定）：

| 形态 | 定义 | 适用档位 |
|---|---|---|
| F1 单重核 | κ∈{core,strong} 且 W≥9（重）的系统 **恰好 1 个**，其余 core/strong 系统 W≤8 | 休闲/中核（默认形态） |
| F2 并联中核 | 0 个重核，≥3 个 W∈[5,8]（中）的 core 系统并联 | 沙盒/模拟经营（星露谷形态） |
| F3 双重核 | 2 个重核，且两者之间必须存在 ≥2 条接口边（强耦合证明，防"两个游戏钉在一起"） | 重核/MMO 档 |
| F0 无重核 | 所有系统 W≤8，core 系统 ≤2 个 | 超休闲 |

**校验算法**：给定系统实例图（每实例带 W 与 κ），数 κ∈{core,strong} 且 W≥9 的实例个数，对照 L0 声明的档位允许形态，不匹配即 block。这是纯计数校验，无自由裁量。

### 3.3 R-C2 重度预算

加权总重度 B(G) = Σ W(S) × weight(κ)，权重：core 1.0 / strong 0.75 / weak 0.5 / meta 0.25。预算上限由 L0 档案决定（初标定，红队可调）：

| 产品档位（L0 已有字段推导：规模 × 单次时长 × 商业模式） | 预算上限 B |
|---|---|
| 超休闲 | 12 |
| 休闲 | 22 |
| 中核单机/网游 | 38 |
| 重核 | 55 |
| MMO/长线运营 | 75 |

超预算 block，且报告按 weight×W 降序列出"最贵的系统"，指向减重度档而非删系统——这直接服务简报 §2.3"重度是谱系"：降重的操作就是把装备从 E4 调回 E2。

### 3.4 R-C3 重度传导

**问题**（简报原文）：装备变重 → 背包/掉落/经济要跟着变重。
**建模**：传导不是玄学感应，传导走的就是 §1.2 的接口边。一条**传导约束** = （源系统, 源维度≥档, 名词, 目标系统, 目标维度≥档），维护在系统模块的 `conduction_rules` 里。机器校验 = 遍历系统实例图每条边，查两端维度档是否满足传导表。

装备系统自带的传导约束（随重度档激活）：

| 装备达到 | 触发的传导约束 | 语义 |
|---|---|---|
| E1（词条，O≥2） | 掉落.D ≥ 1（掉落表须含品质/词条权重列） | 词条从哪来必须有规则 |
| E2（技能 BD） | 技能系统必须存在且 provides 效果定义 | 无技能系统则 E2 档非法（缺边即 block） |
| E3（宝石） | 掉落或商店 provides 宝石实体；背包.D ≥ 1（分类） | 新名词必须有源和存放 |
| E4（合成，O=3） | 掉落 provides 材料实体；背包.D ≥ 2 且 O ≥ 2（分类/堆叠/批量）；货币系统 C ≥ 2（材料回收回路） | 材料经济成环 |

**传导的双向性**：正向（重系统要求承接系统跟上最低档）如上；反向（承接系统超配）只出警告不 block——背包做得比装备需要的重，是浪费不是错误。

### 3.5 三正例 × 三反例

**正例 1（F1 单重核，类幸存者）**：即时战斗 core W9 + 局内构筑 strong W6 + 波次 strong W5 + 局外解锁 meta W4 + 图鉴 meta W3。校验：重核 1 个 ✓；B = 9×1 + 6×0.75 + 5×0.75 + 4×0.25 + 3×0.25 = 19.0 ≤ 22（休闲档）✓；传导：局内构筑 consumes 武器池（战斗 provides）✓。
**正例 2（F1，三消长线）**：三消棋盘 core W10 + 关卡 strong W6 + 体力 strong W3 + 商店/商业化 meta W6 + 赛季 meta W5。B = 10 + 4.5 + 2.25 + 1.5 + 1.25 = 19.5 ≤ 22 ✓；传导：关卡.O3（千级关卡）→ 三消棋盘.D≥2（障碍物/目标类型表足够宽）✓。
**正例 3（F1，战棋 = grid_strategy 重表达）**：回合战斗 core W11（含克制矩阵/地形/命中暴击）+ 兵种成长 strong W7 + 关卡章节 strong W6 + 装备 E0 weak W3。B = 11 + 5.25 + 4.5 + 1.5 = 22.25 ≤ 38（中核）✓。

**反例 1（违 R-C2 + R-C1）**：超休闲跑酷（L0 声明超休闲，B 上限 12）+ 装备 E6（strong W15）。R-C1：超休闲只允许 F0，出现重核 → block；R-C2：仅装备一项加权 11.25，加上跑酷 core 本体必超 12 → block。报告输出："装备系统 W15 超出档位形态，建议降至 E0-E1（W≤7）或改 L0 档位声明。"
**反例 2（违 R-C1 双重核无耦合证明）**：中核卡牌肉鸽声明 F1，却同时配局内构筑 core W13 + 装备 E4 strong W15。两个 ≥重 的 core/strong 系统 → F1 不匹配；即便改声明 F3，装备与卡组之间接口边仅 1 条（装备 modifies 战斗，与卡组零交互）< 2 → F3 的强耦合证明不过 → block。这就是"两个游戏钉在一起"的机器判据。
**反例 3（违 R-C3 传导断裂）**：装备 E4 已选（含合成），但掉落系统未声明 provides 材料实体、背包停在 D=0（单页无分类）。校验器逐条输出："传导约束 [装备E4→掉落 provides 材料] 无满足边——材料无来源"；"传导约束 [装备E4→背包 D≥2] 不满足（当前 D=0）——千级内容无处存放"。两条均 block。

## 5. 与现有 L0-L6 / 决策点模型的关系（保住简报 §3 必保资产）

### 5.1 L 层怎么变

| 层 | 现状 | 新角色 |
|---|---|---|
| L0 | 项目档案 | 不变；**新增产品档位字段**（驱动 §3.2 形态与 §3.3 预算） |
| L1 | 体验方向 | 不变；与系统 A 层主项做一致性弱校验（§1.3） |
| L2 | 品类结构 | **新增必填 `core_loop`（动词序列）**；"品类" 降级为组合模板的名字 |
| L3 | 系统组成决策点 | **升级为系统实例声明层**：从系统库实例化，每实例三元组（系统 id，重度档目标，κ）；组合三规则在此层校验 |
| L4 | 机制规则 | 不变的窄链（决策点→公式→effects→C4 契约），但**归属变了**：决策点住在系统模块内，由重度档激活（E2 档激活 E0-E2 的决策点，E3+ 的不进分母）——这替代了 2575 点的解锁瀑布，直接回应审计 B 的"142 轮 4900 次操作" |
| L5/L6 | 表结构/数值 | 不变；表挂在系统模块下，基数期望按重度档分档给出 |

### 5.2 决策点还剩什么角色

决策点不死，降级为**系统内的机制选择器**——grid_strategy 里 `grid.damage_formula` 那种"攻减防 vs 百分比减伤"的真取舍，正是决策点该干的事，原样保留（含 `requires/conflicts/unlocks`、`parameter_schema`、`effects_template`、`compiler_tags` 全套）。变化只有三点：① 作用域从全局清单收缩到系统模块内部；② 激活主开关从 `unlocks` 瀑布换成重度档（`unlocks` 保留用于系统内的机制依赖，如 `overflow_crit requires hit_chance_formula`）；③ 每个 L3/L4 决策点强制携带 `custom` 入口（见 §6）。

### 5.3 pack 结构怎么变

品类包一分为二：

```
knowledge/design_space/
├── systems/<system_id>/module.json    系统模块：名词端口声明 + 重度分档定义
│                                       （每档：激活的决策点集 + 表 schema + 基数期望 + 传导约束）
│                                       + MDA 三层 + 一致性规则 + effects_template（现 pack 原格式）
└── templates/<template_id>/pack.json  组合模板：系统实例清单（id×重度档×κ）+ core_loop
                                        + 组合校验通过存档 + reference_games + 换皮词表
```

**必保资产逐条对账**（简报 §3）：窄链（决策点→公式→表→C4 契约 + Given/When/Then）→ 原样住进系统模块，一行不改；R1-R7 红线、确定性编译、冻结门、AI 永不代确认 → 全部保留，组合三规则作为冻结门新增第 5 道（在完备度/一致性/换皮/红队之外）；L0-L6 分层意图 → 保留且 L3 更名不改序；Rust 类型基建（DecisionGraph/ParameterSchema/Table/Matrix/ArtifactStore/冻结指纹）→ 全部复用，扩展项见 §7。lane_defense/grid_strategy 两包 → 拆解迁移见 §8。

## 6. 原创入口（Q5，本提案给设计资产侧方案）

**三级入口，成本递增，全部在项目流程内**（终结审计 A"原创唯一入口是去当品类包作者"的死锁）：

1. **机制级 custom**：每个 L3/L4 决策点强制带一个 `custom` 选项，schema 为结构化四元组（归属系统 + rule_text 公式文本 + effects_template + 参数约束）——不是自由文本，是和预设选项同构的机制描述。冻结门单列 custom 计数，红队按 §6 评审标准重点审。这是审计 B 整改建议 1 的采纳。
2. **重度档级 custom**：在库内系统上加自定义子机制（如给装备加"装备觉醒"档）：声明新增子机制/表/边，重度五维**重算**（量表是可数的，所以 custom 也能算分），传导约束按新档重查。
3. **系统级 custom**：新建库外系统：填系统模块 schema（名词端口 + MDA 三层 + ≥1 个 L4 机制或声明借用库内机制 + 重度自评五维计数）。机器校验结构完整性（三测试的可机检部分：有独占表？有名词转换？），红队人工审边界与重度自评。

**与既有硬规则的协调**：
- `reference_games ≥ 3`：对**组合模板**维持硬要求（模板是复用资产，必须有校准源）；对**系统级 custom** 降为"≥1 参考或显式声明无参考"，无参考时强制走红队加严通道（评审时间加倍 + 主创署名确认）——原创混合玩法找不到 3 个参考是逻辑事实，硬卡是死锁（审计 A 实证），放行 + 加严是唯一自洽解。
- R5 换皮扫描：只对模板来源内容比对，custom 内容天然豁免换皮（自己写的谈不上换谁的皮），但 custom 计数进冻结报告防"全项目都是 custom 绕开设计空间"（阈值建议：custom 决策 >40% 出警告）。
- rationale 进链：采纳审计 B 建议 1——custom 与预设选择的 rationale 一律进 C0 的 `design_notes`，进 C2 的 source_text 与 C4 机制上下文。这是设计资产侧要求，实现归 B。
