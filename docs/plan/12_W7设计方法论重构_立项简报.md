# W7 立项简报：设计方法论重构（系统组合 × 重度模型）

> 2026-09-02 主开发起草。本简报是多 agent 设计商讨的**共同真源**：所有提案、评审、综合都以本文件为出发点。
> 状态：商讨中，未定稿。定稿后将取代/修订 `docs/design/01`（决策模型与设计空间）。

## 1. 为什么立项：四个大版本都倒在设计层

- v1（Python）/ v2（RUST）/ v3（NEWrust 计划）/ v4（当前）每次超大版本重写，根因都是设计层表达力不足。
- 2026-09-02 两份独立审计（本目录 `2026-09-02_设计方法论审计A_覆盖度.md`、`_审计B_全链演练.md`）给出 3/10 与 2.5/10：
  - 通用层 2575 点是问卷冲压（130 套选项复制），对下游产出贡献≈0；
  - 25 份逆向模板证据自引用、跨品类答卷全同，属负资产；
  - 10 款跨品类游戏 47 条核心机制仅 4% 可直接表达、64% 无表达位；
  - 原创机制没有结构化入口，rationale 被 C0 丢弃，到 C4/C6 彻底消失；
  - EffectSpec 七封闭枚举是架构级天花板（位移/规则修改器/图结构/连续曲线/时序均无表达位）。

## 2. 用户设计愿景（2026-09-02 原意，逐条保真，本轮商讨的目标形态）

1. **玩法由系统组合而成**：一个完整玩法（gameplay）= 多个"系统功能模块"的组合（装备、宠物、背包、任务、抽卡、社交……）。
2. **系统跨玩法复用**：装备系统可以出现在 A 玩法，也可以出现在 B 玩法、C 玩法——系统是独立于玩法的可复用积木。
3. **每个系统有"重度"维度**：同一个装备系统，轻 = 只有属性加成；重 = 属性 BD + 技能 BD + 宝石镶嵌 + 装备合成 + 冶炼 + 升级 + 强化……重度是一个谱系，不是开关。
4. **组合合理性规则**：一般只需要**一个与核心玩法强关联的重度系统**，其余都是辅助的轻度系统；一个系统的"重"会影响其他系统的"重"（重度之间存在相互约束/预算关系）。
5. **理论锚点 MDA**（Mechanics-Dynamics-Aesthetics）：现有"选择式设计 + 内容填充"就是从 MDA 出发的，但内容提炼不够——需要把"重"这个概念做成可评定、可校验的模型。
6. **待解的两个核心问题**：①如何评定"重"（重度的构成与量化标准）；②玩法怎么组合才合理（组合规则的表达与机器校验）。

## 3. 必须保留的资产（审计确认为真的部分，不许推倒）

- **pack → 公式 → 表结构 → C4 能力契约**这条窄链（`grid.damage_formula` 式的真机制表达，带 Given/When/Then 验收场景）。
- R1-R7 红线、确定性编译（只映射不发明）、冻结门纪律、AI 永不代确认。
- L0-L6 分层的**意图**（战略→机制→数据逐层下钻）；但 L4 的表达力必须扩展。
- 现有 Rust 类型基建（DecisionGraph/ParameterSchema/Table/Matrix/ArtifactStore/冻结指纹）能复用则复用。

## 4. 已证实的失败教训（提案不许重蹈）

1. 冲压式问卷不是设计空间——每个决策点必须是真实的、互斥有代价的设计取舍。
2. 原创无入口 = 设计师枷锁——新系统/新机制必须有一等公民入口，且与认证/红线纪律兼容。
3. 封闭效果枚举装不下真实游戏——类型系统必须扩展（但不能牺牲确定性编译）。
4. 证据自引用的模板是负资产——宁缺勿造。
5. "覆盖很广的假象"比"没覆盖"更害人——覆盖度声明必须可被压力测试证伪。

## 5. 提案必须回答的七个问题（Q1-Q7）

- **Q1 系统本体模型**：什么是一个"系统"？边界怎么划（装备/宠物/背包是三个系统还是一个成长系统的三面）？系统的接口（对外暴露什么、消费什么）？与 MDA 三层怎么映射（系统的 Mechanics 决策 → 期望产生的 Dynamics → 服务的 Aesthetics）？
- **Q2 重度模型**：重度由什么构成（子机制数量？数值深度？交互面宽度？玩家心智负担？）？如何分档（轻/中/重还是连续分值）？"评定重"的可操作标准——给出装备系统从最轻到最重的完整谱系作为标定样例（属性加成 → +技能BD → +宝石 → +合成/冶炼 → +升级/强化 → +套装/幻化…）。
- **Q3 组合规则**：核心系统 × 辅助系统的约束如何表达与机器校验？（重度预算？系统间耦合矩阵？与核心循环的关联强度？）"一个重度核心 + 若干轻度辅助"如何成为可校验的规则而非口号？重度相互影响（装备重了背包就得跟着重）怎么建模？
- **Q4 覆盖性证明**：该模型下，审计 A 的 10 款游戏（幸存者/星露谷/杀戮尖塔/CS2/旷野之息/三消/MOBA/棋牌/音游/极乐迪斯科）各自被表达成"哪些系统 × 什么重度 × 什么组合"？逐款给出表达路径；装不下的如实标注并说明属于哪类缺口。
- **Q5 原创入口**：设计师要做预设系统库里没有的新系统/新机制，流程入口在哪？（custom 系统/机制的 schema 是什么、走什么认证、红队怎么审？）与 R5 换皮扫描、reference_games≥3 这类既有硬规则怎么协调？
- **Q6 类型系统落地**：决策点模型、EffectSpec、参数 schema 各要怎么改，才能承载 Q1-Q3 且保持 C0-C6 确定性派生？（分层效果体系？图类型参数？重度作为一等类型属性？）对现有 13 个 crate 的冲击面评估。
- **Q7 迁移路径**：现有资产怎么处置（v2 2575 点、25 份模板、lane_defense/grid_strategy 两包、已有 C0-C6 编译器）？分几波落地？第一个可信的垂直样板选什么（建议：用新模型重表达 lane_defense + 一款审计中 ❌ 最多的游戏做对照）？

## 6. 评审标准（红队按此打分，1-10）

1. **覆盖度**：10 款审计游戏 + 装备系统全谱系的可表达比例。
2. **重度模型可操作性**：一个真实系统策划能否用它评定/沟通"重"。
3. **组合规则可校验性**：能否落成机器校验（而非人工自由裁量）。
4. **可编译性**：能否确定性派生 C0-C6（不发明内容）。
5. **原创友好度**：预设外设计的进入成本。
6. **迁移现实性**：从现状到新模型的工程代价与风险。
