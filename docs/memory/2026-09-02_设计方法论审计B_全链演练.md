## ② 原创机制归宿追踪

**机制 A：可编程索敌（条件-动作规则）**

| 站点 | 归宿 |
|---|---|
| 输入 | 系统没有任何决策点涉及"索敌/目标选择"（2575 个通用点关键词零命中）。唯一入口是 `u.experience` 的 `statement` 自由文本参数（全空间**仅 2 处**自由文本入口）+ 各决策点的"选择理由"字段 |
| 探针 A | 尝试给守卫表加 `targeting_rule` 列 → 未报错也未保留语义，只作为无 schema 的裸字段存在；表结构（列集合）不可扩展，`is_custom` 选项也只允许"标识列+一个数值列"的退化结构 |
| 冻结 v1 | statement 与理由文本原样冻结 |
| C0 | **statement 被丢弃**（编译器只取 `promise` 角色的 rationale 进 `experience_promise`），"可编程"仅存活在项目名里 |
| C2 | 叙述由 AI 写——**唯一传递点**。我在 scripted 应答里主动写了它，它就在；换个偷懒的 AI（或复读模板），它就没 |
| C4/C6 | **彻底消失**。C4 无索敌相关能力契约，C6 无对应任务 |

**机制 B：波次自适应变异**

| 站点 | 归宿 |
|---|---|
| 输入 | 塞进 `ld.wave_system` 的选择理由 +敌人表探针列 `mutation_traits`（校验器静默放行未知列——注意：AI 提案路径会查"发明字段"，用户手填不查，双标）+ 变异载体敌种 `adapt_mimic` |
| C0 | 理由文本全部丢弃（source_map 只存"spec 路径 ↔ 决策 id"映射，不存 rationale）；`mutation_traits` 作为裸行数据存活在敌人表 rows 里，但**列 schema 里没有它**——下游没人知道这个字段是什么 |
| C3 | `adapt_mimic` 拿到一条美术资产需求，与普通敌人无异，变异语义为零 |
| C4 | **彻底消失** |
| C6 | 只剩一行"制作资产 asset_ld.enemy_roster.adapt_mimic"——**核心玩法机制降级为一张怪物贴图任务** |

**结论**：两个原创机制的最终归宿是——A 只活在 AI 生成的概览叙述一段话里；B 只活在一个敌人 id 和一个无 schema 的裸字段里。**没有任何结构化通道让预设选项之外的机制变成"需求"。**

## ③ C4 / C6 摘录点评

**摘录 1（C4 全文的 1/3，共 1277 字节）**：

```6:13:V4/.adm4_data/.../C4/document.md
## CounterDamageResolver（`cap_ld.counter_damage`）
- 来源：`mechanics/ld.counter_damage`
- 数据结构：
- 验收场景：
  - Given 系统 ld.combat_system 处于就绪状态
  - When 克制系数乘法公式。伤害 = 攻击力 × 克制系数（系数来自克制矩阵）（base_multiplier=1.5）
  - Then 实体 ld.enemy_roster 的 hp 按公式 hp - attack * counter_coeff * 1.5 变化
```
**对开发者有用**，因为它给了公式、带回填参数值（1.5）、还有 Given/When/Then 验收骨架——这是全链最接近"需求"的东西。但"数据结构："后面是**空的**（effects 引用的是表 id 而非实体 id，收集逻辑落空），且**全项目只有 3 个这样的契约**。一个塔防最少要有：索敌、弹道、生命/死亡、波次调度、胜负判定、UI——这里一个都没有。

**摘录 2（C6 任务表头部）**：

```3:10:V4/.adm4_data/.../C6/document.md
- 任务总数：115（程序 3 / 资产 11 / 装配 101）
| 实现 CounterDamageResolver | program | - |
```
程序任务 **3 个**、依赖关系基本全空（115 个任务里只有 3 条依赖边）。**没用**，因为一个排期工具最基本的价值就是依赖序，而这里资产、装配、程序三类任务互相无关联，等于把三张清单钉在一起。

**摘录 3（C6 装配任务，101 条中的典型 6 条）**：

```31:36:V4/.adm4_data/.../C6/document.md
| 装配系统 难度压强（主选） | assembly | - |
| 装配系统 难度压强（主选） | assembly | - |
| 装配系统 难度压强（主选） | assembly | - |
```
**完全没用**。"难度压强（主选）"重复出现 6 次（6 个不同的 v2 平衡决策点选了同一个选项标签，渲染时只剩标签），开发者面对"装配系统 公平感（主选）×6"无法产生任何动作。这 101 条就是**把我的 v2 点选记录换了个动词重新打印**——这是"决策选项复述"的铁证。

**摘录 4（C2 系统章节，101 章中的 100 章长这样）**：

```12:14:V4/.adm4_data/.../C2/document.md
## 系统：网格部署
本系统按已冻结的决策选择运转：所选选项、参数与理由如契约所载。……
```
**没用**，且责任在流程设计而非 AI：C2 给 AI 的 `source_text` 只有选项 label + summary + implications，我写的选择理由（变异器的输入输出设计全在理由里！）**根本不进 AI 的上下文**。巧妇难为无米之炊。

**摘录 5（C3 资产需求，11 条全同文）**：

```10:12:V4/.adm4_data/.../C3/document.md
- 实体：`ld.enemy_roster.swarm_crawler`
- 画面描述：占位画面描述：该实体为通道塔防中的战斗单位，需体现其职能辨识度……
```
**几乎没用**：实体属性（速度 2.6 的飞行单位 vs 护甲 18 的重甲慢速单位）明明在表里，但传给 AI 的 user_prompt 只有属性**键名**不含值，11 个形态迥异的单位拿到同一段描述模板。画师拿到这个只会来问你要真正的设定。

**信息增量总结**：相对我的决策清单，C0-C6 的真实增量 = 3 个带公式的能力契约 + 4 张数值表的结构化转录 + 波次内容数据 + 资产清单的枚举。这些全部来自 lane_defense 品类包的 15 个决策点。**其余 2575 个通用点贡献的增量≈0**（在 C0 变成 101 个空壳 SystemSpec，在 C6 变成 101 条不可执行的装配任务）。

## ④ 打分表 + 裁决

| 维度 | 分 | 依据 |
|---|---|---|
| 表达自由度 | **2/10** | 全空间 2 个自由文本参数、6 个退化 custom 选项；原创机制只能寄生在理由字段，而理由字段被 C0 丢弃 |
| 辅助真实性 | **5/10** | 完备度/主选/参数范围/行引用一致性检查全部真实有效（基数下限拦截、`TypedValue` 校验都对）；但未知列静默放行（双标）、红队可自证、报错不给格式示例 |
| 拆解增值度 | **3/10** | 品类包覆盖段有真拆解（公式/表/验收场景）；v2 通用层 2575 点的拆解产物是零信息量复读，且占产物体量的绝大部分 |
| 需求可执行度 | **2/10** | C4 只有 3 个契约、数据结构字段为空、无 UI/无索敌/无波次调度需求；C6 的 101/115 任务不可执行、依赖图缺失。没见过项目的程序员**不能**按它开工 |
| 全流程可用性 | **1/10** | 手动路径约 4900 次 CLI 操作（人力 40+ 小时），预填路径反而更糟（2585 confirm + 2574 set-primary + 2585 理由改写）；真实设计师第二天不会回来 |
| **总分** | **2.5/10** | |

**一句话裁决**：这是一台把"塔防品类包里预设好的 15 个决策"拆解得像模像样、同时把你自己的游戏创意系统性过滤掉的机器——它输出的不是你的游戏的需求文档，而是它的选项库的使用报告。

## ⑤ 给主开发的前 3 条整改建议

1. **让理由与自由文本进入编译链，而不是只进档案**。C0 丢弃 rationale 和 statement 是原创性消失的直接原因。最小改动：`SystemSpec` 增加 `design_notes` 字段收编所选项的 rationale，C2 的 `source_text` 与 C4 的机制上下文都带上它；再给每个 L3/L4 点加一个通用的 `custom_mechanic`（自由 rule_text + 自定义 effects）选项，让"预设外机制"有一等公民入口。

2. **砍掉或折叠 v2 通用层的解锁瀑布**。2575 个点、每答 16 个解锁 16 个、绝大多数是"用哪种感受推进某某判断"的五选一——它贡献了 98% 的操作量和 0% 的 C4 增量。建议：v2 层默认按品类包给出整包预设，只让用户改例外（现在的"预填"不算数，因为 confirm/set-primary/改理由三件套让它比从零还贵）；多选点确认时缺主选应一步交互完成而不是两个命令两次报错。

3. **C6 装配任务合并去重 + 补依赖，否则删掉**。同名装配任务重复 6 次、115 任务 3 条依赖边，这样的"开发计划"会直接摧毁工具在程序员面前的信誉。装配任务应按 `spec_role`/domain 聚合成"实现平衡调参框架（覆盖 6 个平衡决策）"级别的条目，并从 `unlocks`/`requires` 图自动生成依赖边；同时把 C3 的 user_prompt 从"属性键名"改成"属性键值对"，让 11 条资产需求不再是同一句占位话。

**附带如实声明**：本次演练所有 AI 环节（冻结红队、C1 红队、C2 叙述、C3 描述、C4 命名）均因本机无 API key 走 `--scripted-file` 通道，应答由审计人撰写——这意味着上述产物中所有"AI 增值"部分是本次演练的上界估计；真实 AI 的 C2 叙述可能更好，也可能更差，但 C4/C6 的结构性缺陷与 AI 质量无关。
