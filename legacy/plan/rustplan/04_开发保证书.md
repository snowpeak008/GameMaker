# AutoDesignMaker Rust 重建开发保证书

> 本文件是 Rust 重建工程的承诺清单。它不是口头保证“没有 bug”，而是定义每一阶段必须遵守的工程底线和验收条件。

---

## 一、总体保证

开发方必须保证：Rust 版是 `RUST/` 下的完整重建项目，不以 Python 运行时代码作为产品依赖。

具体承诺：

1. 不把 Python 代码作为 Rust 产品运行层。
2. 不把旧 Python 模块结构作为 Rust 架构。
3. 不把旧存档格式作为 Rust 存档格式。
4. 不把旧 Step 编号作为 Rust 流水线强制边界。
5. 不把旧测试通过作为 Rust 正确性的证明。
6. 不把 AI 输出视为天然可信结果。
7. 不把 GUI 代码作为业务规则所在地。

---

## 二、架构保证

Rust 工程必须使用 Cargo workspace。

保证：

- 重复使用的内容拆到基础 crate。
- 独立业务边界拆到独立 crate。
- 正式存档业务由独立 crate 拥有。
- UI 不直接访问文件系统核心写入。
- AI Provider 不污染业务 crate。
- pipeline 不绕过 runtime。

不允许：

- 单一巨型 crate 承担全部职责。
- GUI crate 直接处理正式保存事务。
- Stage 直接写正式存档。
- 业务 crate 直接读写 provider key。

---

## 三、数据安全保证

Rust 版必须保证用户项目数据不会因为普通运行失败而被静默破坏。

正式保存必须满足：

1. 有 archive lock。
2. 写入临时目标。
3. 校验内容。
4. 原子提交。
5. 失败保留旧正式存档。
6. 记录保存事件。

多开必须满足：

1. 每次双击独立 Session。
2. 每个 Session 独立 Draft。
3. 不同 Archive 可并行。
4. 同一 Archive 第二个编辑会话被拒绝。
5. 错误提示用户可理解。

---

## 四、AI 保证

AI 是核心能力，但必须被管控。

保证：

1. AI Provider 可插拔。
2. 业务只依赖 AI capability。
3. AI task 有记录。
4. AI 输出有 raw/parsed/validated/accepted 状态。
5. AI 输出失败可诊断。
6. AI 不可用时 UI 能解释原因。
7. AI 不得绕过质量门。

不保证：

- 任意 AI 一定生成高质量内容。
- 第三方 Provider 永远可用。
- 网络失败时能完成 AI 任务。

但必须保证：

- 失败可见。
- 失败可记录。
- 失败不破坏项目状态。

---

## 五、流水线保证

第一版 Rust 流水线必须保证确定性优先。

保证：

1. 同一项目内串行执行。
2. stage 依赖明确。
3. stage 输入输出明确。
4. stage 失败可解释。
5. stage 产物可验证。
6. stage run state 可恢复。
7. 停止请求在安全边界生效。

不允许：

- 第一版默认同项目并发。
- 没有依赖图就并发执行。
- 阶段直接修改正式存档。
- 阶段无日志运行。

---

## 六、GUI 保证

Rust GUI 必须服务业务，而不是拥有业务。

保证：

1. 双击可启动程序。
2. 每次启动独立进程。
3. GUI 长任务不冻结主界面。
4. GUI 显示任务进度和错误。
5. GUI 通过 command 调用 application service。
6. GUI 不直接执行正式保存事务。

Slint 方向必须经过 POC 验证。

若 Slint 无法承载真实复杂界面，必须形成新的 ADR 后才能更换技术路线。

---

## 七、测试保证

每个框架阶段必须先有测试。

最低测试命令：

```bash
cargo fmt --check
cargo check --workspace
cargo test --workspace
```

必须覆盖：

- foundation
- config
- archive
- runtime
- AI mock
- validation
- pipeline mock
- design model
- SDK model
- packaging model
- UI view model

禁止：

- 依赖真实 AI 作为单元测试。
- 依赖真实用户目录。
- 依赖旧 Python 运行时。
- 依赖固定绝对路径。

---

## 八、文档保证

每个不可逆决策必须有 ADR。

必须文档化：

- 为什么这样做。
- 替代方案是什么。
- 后果是什么。
- 哪些内容不能做。

`CONTEXT.md` 只写术语，不写实现计划。

`plan/rustplan/` 写实施计划。

`knowledge/decisions/` 写不可逆决策。

---

## 九、迁移保证

当前 Python 项目仅作为参考项目。

保证：

1. 不迁移 Python 运行时代码。
2. 不承诺旧存档兼容。
3. 不承诺旧 draft 兼容。
4. 不承诺旧 schema 兼容。
5. 不承诺旧 GUI 行为逐像素一致。

可以迁移：

- 术语
- 业务流程经验
- 架构教训
- 游戏设计知识
- SDK 内容
- 模板内容
- prompt 思想

但迁移后必须：

- 符合 Rust 新 schema。
- 有 Rust loader。
- 有 Rust test。
- 不依赖旧路径。

---

## 十、阶段验收保证

任何阶段不得只以“代码写完”作为完成。

完成必须同时满足：

1. 代码完成。
2. 测试完成。
3. 文档更新。
4. 错误路径覆盖。
5. 日志路径覆盖。
6. 无 Python runtime 依赖。
7. 无硬编码用户路径。
8. 与既定 ADR 不冲突。

---

## 十一、风险声明

本重建是大工程，以下风险不能被隐藏：

1. Rust GUI 复杂度风险。
2. Slint 控件能力风险。
3. AI Provider 接入差异风险。
4. 旧知识数据质量风险。
5. 阶段模型重设风险。
6. 存档格式重设风险。
7. 多进程锁在 Windows 下的边界风险。
8. Unity/外部项目写入边界风险。

保证不是承诺没有风险，而是承诺：

- 风险被记录。
- 风险有验证任务。
- 风险失败时不静默推进。

---

## 十二、签署式结论

Rust 重建必须以工程可靠性为第一优先级。

在底层框架完成前，不应追求完整业务演示。

在数据安全、存档锁、AI 输出验证、任务日志、测试框架没有完成前，不应开始大规模迁移业务链条。

最终交付必须是一个可双击启动、可多项目并行、可安全保存、可按需 AI 介入、可运行游戏设计与开发流水线、可打包、可管理 SDK 知识的 Rust 桌面工作台。
