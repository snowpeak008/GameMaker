# Rust 框架优先开发计划

> 开发原则：先骨架，后链条；先边界，后业务；先验证，后扩展。

---

## Phase 00：项目决策冻结

### 目标

把 Rust 重建的不可逆决策固定下来，避免开发中反复摇摆。

### 输入

- `CONTEXT.md`
- `knowledge/decisions/ADR-2026-07-04-*.md`
- `knowledge/decisions/ADR-2026-07-05-*.md`
- `plan/rustplan/*.md`

### 输出

- Rust 产品范围冻结
- Rust workspace 边界冻结
- 存档模型冻结
- AI 介入模型冻结
- GUI 技术方向冻结
- 流水线第一版串行冻结

### 验收

- 所有关键决策都有 ADR。
- `plan/rustplan/` 有总纲、矩阵、计划、注意事项、保证书。
- 没有未解释的“先兼容 Python”要求。

## Phase 01：Cargo workspace 骨架

### 目标

建立 `RUST/` 下的 Rust 工程结构。

### 目录

```text
RUST/
  Cargo.toml
  apps/
    adm-desktop/
    adm-cli/
  crates/
    adm-foundation/
    adm-config/
    adm-archive/
    adm-runtime/
    adm-ai/
    adm-pipeline/
    adm-design/
    adm-development/
    adm-assets/
    adm-packaging/
    adm-sdk/
    adm-ui-model/
    adm-validation/
    adm-testkit/
  resources/
  docs/
  tests/
```

### 任务

1. 创建 workspace。
2. 每个 crate 创建最小 `lib.rs`。
3. `adm-cli` 创建最小命令入口。
4. `adm-desktop` 创建最小 Slint POC 入口。
5. 统一 Rust edition、lint、format、dependency policy。

### 验收

- `cargo fmt --check` 通过。
- `cargo check --workspace` 通过。
- `cargo test --workspace` 通过。
- `adm-cli --version` 可运行。
- `adm-desktop` 可打开空窗口。

## Phase 02：foundation 基础类型

### 目标

统一所有 crate 的基础类型和错误边界。

### 必做类型

- `ProjectId`
- `ArchiveId`
- `SessionId`
- `RunId`
- `StageId`
- `TaskId`
- `ArtifactId`
- `ProviderId`
- `UtcTimestamp`
- `ContentHash`
- `SafePath`

### 必做能力

- ID 生成
- 时间生成
- hash 计算
- 路径安全检查
- 原子写文件
- JSON/TOML 读写封装
- 统一 error enum
- `AdmResult<T>`

### 验收

- 所有 ID 可序列化/反序列化。
- 路径不能逃逸 root。
- 原子写失败不会留下半文件。
- 错误信息包含上下文。

## Phase 03：配置系统

### 目标

建立 Rust 版配置模型，不兼容旧 `settings/`。

### 配置分类

1. 应用配置
2. 用户配置
3. AI Provider 配置
4. 项目默认配置
5. SDK 索引配置
6. GUI 配置

### 规则

- API key 不写入项目正式存档。
- provider 配置支持可见诊断。
- 配置读写必须经过 `adm-config`。
- 业务 crate 不能直接读配置文件。

### 验收

- 空配置能启动。
- 缺失 AI key 显示可诊断状态。
- 配置 schema 版本可升级。
- 测试不会读用户真实配置。

## Phase 04：正式存档、临时工作区、导出包

### 目标

实现 Rust 版项目数据安全基础。

### 内部目录建议

```text
archives/{archive_id}/
  archive.toml
  project/
  design/
  pipeline/
  package/
  sdk/
  attachments/
  history/

drafts/{session_id}/
  draft.toml
  project/
  design/
  pipeline/
  package/
  sdk/
  runtime/
  logs/
```

### 存档锁建议

```text
archives/{archive_id}/.lock/
  owner.toml
  heartbeat.toml
```

owner 字段：

- archive_id
- session_id
- process_id
- executable_path
- started_at
- acquired_at
- lock_nonce

### 必做操作

- 创建空 draft
- 创建 formal archive
- 打开 archive 到 draft
- 保存 draft 到 archive
- 获取 archive lock
- 释放 archive lock
- stale lock 检测
- export package
- import package

### 保存事务

正式保存必须使用事务流程：

1. 校验 archive lock。
2. 从 draft 生成保存计划。
3. 写入临时目录。
4. 校验内容指纹。
5. 原子替换正式目录。
6. 写入保存事件。
7. 更新 UI 状态。

### 验收

- 两个不同 archive 可同时打开。
- 同一个 archive 第二次打开被拒绝。
- 保存失败不破坏旧 archive。
- 强制中断后 stale lock 可诊断。
- export package 可导出。
- import package 可导入为新 archive。

## Phase 05：runtime 任务系统与日志

### 目标

建立所有长任务的统一运行机制。

### 任务状态

- pending
- running
- waiting_input
- completed
- failed
- cancelled
- blocked

### 事件类型

- session_started
- archive_opened
- archive_saved
- task_started
- task_progress
- task_completed
- task_failed
- ai_intervention_requested
- ai_intervention_completed
- pipeline_stage_started
- pipeline_stage_completed
- validation_failed

### 日志要求

- JSONL 结构化日志
- human-readable summary
- 每个 session 独立日志
- 每个 run 独立日志
- GUI 可过滤

### 验收

- 长任务可启动。
- 长任务可停止。
- 失败有 error chain。
- 日志可按 task/run/stage 查询。
- 无 GUI 时 CLI 也可运行任务。

## Phase 06：AI Provider 框架

### 目标

建立可插拔 AI 能力，不绑定具体供应商。

### trait 建议

- `TextGenerationProvider`
- `StructuredGenerationProvider`
- `ReviewProvider`
- `CodeGenerationProvider`
- `ImageGenerationProvider`
- `SdkAssistProvider`
- `LongTaskProvider`

### AI Task 记录

每次 AI 介入必须记录：

- task_id
- provider_id
- capability
- prompt/input reference
- output reference
- started_at
- completed_at
- status
- token/cost metadata
- validation result
- accepted/rejected

### 验收

- mock provider 可跑完整测试。
- provider 不可用时显示诊断。
- AI 输出不经验证不能写入 accepted state。
- 结构化输出失败有重试/失败记录。

## Phase 07：validation 与 schema 框架

### 目标

建立 Rust 新数据模型的验证能力。

### 范围

- archive schema
- draft schema
- design schema
- pipeline stage schema
- artifact schema
- AI task schema
- package manifest schema
- SDK resource schema

### 规则

- Rust type 是第一权威。
- schema 是导出/验证工具。
- 不以旧 Python schema 为权威。

### 验收

- 每个核心模型可序列化。
- 每个核心模型可反序列化。
- 无效样本被拒绝。
- 错误路径清晰。

## Phase 08：pipeline 框架

### 目标

实现阶段化流水线的 Rust 框架，不实现完整业务阶段。

### 必做对象

- `Stage`
- `StageInput`
- `StageOutput`
- `StageStatus`
- `StageGate`
- `ArtifactContract`
- `PipelineGraph`
- `PipelineRunner`
- `PipelineRunState`

### 第一版执行

- 同一项目串行。
- 支持阶段依赖。
- 支持阶段跳过。
- 支持阶段失败。
- 支持 AI 介入点。
- 支持 validation hook。

### 验收

- 构造三个 mock stage：A -> B -> C。
- A 失败时 B/C 不执行。
- B 请求 AI intervention 时 run state 可见。
- C 成功后 artifact report 可见。
- 停止请求在阶段边界生效。

## Phase 13：最小业务链条

### 目标

框架通过后，再写第一条业务链。

建议链条：

1. 新建项目
2. 填写项目画像
3. 设计完整度评分
4. AI 介入补全
5. 生成开发计划草案
6. 生成打包报告草案
7. 保存正式存档
8. 导出项目包

### 验收

- 完整链条只依赖 Rust。
- 每一步都有日志。
- 每一步都有验证。
- 保存/退出/重开后状态一致。

## Phase 14：旧功能系统性重建

### 范围

- 完整设计工作台
- 完整阶段流水线
- 开发任务
- 美术任务
- 打包任务
- SDK 知识库
- AI Provider 实现
- GUI 完整面板

### 原则

- 一次只重建一个领域。
- 每个领域先模型、再服务、再 UI。
- 不允许 UI 先行定义数据结构。

---

## 总体验收线

Rust 框架阶段完成的最低标准：

1. `cargo test --workspace` 通过。
2. `cargo check --workspace` 通过。
3. 桌面空壳可启动。
4. CLI 可执行基础命令。
5. archive/draft/lock 测试通过。
6. runtime task/log 测试通过。
7. AI mock provider 测试通过。
8. pipeline mock stage 测试通过。
9. Slint POC 通过。
10. 没有 Python runtime 依赖。
