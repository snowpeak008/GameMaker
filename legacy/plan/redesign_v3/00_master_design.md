## 2. 体系总览

```
【设计阶段】                                【生产阶段】
决策工具（两模式）                          流水线 Phase 1：文档编译（C0-C6）
 ├─ 手动选择模式                             ├─ C0 规格编译（决策→GameSpec，确定性）
 ├─ AI 访谈模式（逐条确认）                  ├─ C1 静态验证 + AI 红队评审
 │                                           ├─ C2 玩法设计文档（契约渲染）
 ├─ 模板预填（逆向答卷）───换皮门───┐        ├─ C3 内容与资产需求
 │                                  │        ├─ C4 程序需求与架构
 └─ 设计冻结门 ◄────────────────────┘        ├─ C5 美术方向与风格锚点【人工门】
        │                                    └─ C6 开发计划 +【Phase1 签收人工门】
        ▼                                    流水线 Phase 2：EXE 生产（P0-P5）
   冻结决策集（唯一内容真相源）               ├─ P0 工作区种子
                                             ├─ P1 程序任务执行（复用 v2 ChangeKernel）
【模板生产线】（独立于项目流程）              ├─ P2 资产批量生产【清单人工门】
 逆向工具链：检索→填答→标源→人工审核→认证    ├─ P3 装配与集成
                                             ├─ P4 验收场景执行
                                             └─ P5 打包交付
```

核心不变式：**内容只在决策工具里创作一次；此后每一步都是从 GameSpec 的确定性派生或经门禁的 AI 加工，任何步骤不得引入决策集里不存在的设计内容。**

## 3. 决策工具设计

### 3.1 L 层梯度（重新定义）

| 层 | 名称 | 回答的问题 | 示例（通道塔防） |
|----|------|-----------|-----------------|
| L0 | 项目档案 | 平台/商业模式/规模/合规（非玩法） | PC 单机 premium，medium 规模 |
| L1 | 体验方向 | 核心情感与幻想是什么 | 「以小博大守护脆弱生态」 |
| L2 | 品类结构 | 什么品类、什么模式结构 | 通道塔防 + 波次关卡制 |
| L3 | 系统组成 | 有哪些系统、系统间接口 | 部署系统/资源系统/波次系统/克制系统 |
| L4 | 机制规则 | 每个系统的规则与状态机（公式符号级） | 克制伤害 = 基础×克制系数；部署冷却机制 |
| L5 | 实体与参数结构 | 实体类型、属性表结构、关系表结构 | 守卫 5 种 × {成本,攻速,射程,克制标签}；克制矩阵 5×4 |
| L6 | 数值表 | 具体数字、曲线、关卡数据 | 每个守卫的具体数值；10 关波次表 |

**项目深度档（Depth Profile）**：项目创建时选定目标层（最低 L4，可选 L5/L6），全局统一。冻结门按选定深度检查完整性——选 L6 而数值表空 = 不能冻结。选 L4 的项目，Phase 1 文档会显式标注「数值层留待开发期填充」，且不可进入 Phase 2。

### 3.2 决策点数据模型（枚举选项 + 参数）

```jsonc
DecisionPoint {
  id, domain, level,                 // 所属领域、所属 L 层
  genre_scope,                       // "universal" | "pack:<genre_id>"
  question,                          // 一句话问题
  options: [{
    id, label, summary,
    implications: [string],          // 选它意味着什么（供用户/AI 判断）
    requires: [decision.option],     // 前置约束
    conflicts: [decision.option],    // 冲突约束
    parameter_schema: {...}          // 选定后要填的参数（typed；L5/L6 层为表结构 schema）
  }],
  skin_fields: [path],               // 哪些参数属于"皮"（命名/主题/文案），换皮门只查这些
  evidence_slots: true|false         // 模板逆向时此决策点是否需要来源标注
}

Selection {                          // 一次选择的记录
  decision_id, option_id, parameters,
  rationale,                         // 为什么选（用户写或 AI 访谈生成）
  provenance,                        // "user_manual" | "ai_interview_confirmed" | "template:<id>"
  confirmed_by_user: bool            // AI 访谈模式必须为 true 才计入完成度
}
```

要点：
- **选项是封闭枚举**，创新玩法通过「选项 + 参数」表达而不是自由文本；确实无法归入任何选项时，该决策点提供显式的 `custom` 选项，但 `custom` 会在冻结门要求额外的机器可判定描述（结构化字段，不是散文），并在报告中计数——`custom` 比例过高说明品类包选项设计有缺口，反馈给品类包维护。
- **L5/L6 的参数就是表**：parameter_schema 直接定义实体属性表/克制矩阵/波次表的列结构，L6 填行数据。这使「数值表」成为决策的一部分而非流水线的发明。
- 决策点之间用 requires/unlocks 组成有向无环图（沿用现有 domains 的图结构，但节点全部重做）。

### 3.3 两种作业模式

**模式 A：手动选择。** 用户在决策图上逐点选择选项、填参数。UI 按领域 × L 层组织，实时显示完成度（按深度档计）与约束冲突。

**模式 B：AI 访谈（分层逐条确认）。** 流程：
1. AI 读取概念输入（概念文档/口述），按决策图拓扑序逐点提案：「建议选 X，理由…，参数建议…」
2. 用户对每条：确认 / 改选 / 改参数 / 跳过（跳过项留待手动）
3. 只有 `confirmed_by_user=true` 的选择计入完成度——**AI 不能替用户完成任何决策的最终提交**
4. 访谈可分多次进行，进度持久化

两模式可混用（访谈完成 80%，手动补 20%）。AI 不可用时模式 B 整体不可用（显式提示），模式 A 始终可用——这满足「AI 必需即停」而不会把设计工具本身锁死。

**确认粒度分层（解决"决策点多 + 逐条确认"的冲突）。** 详细度越高决策点越多，逐条确认几百条会逼出橡皮图章。两条解耦：
- **详细度 ≠ 决策点数量**：真正的详细度住在 L5/L6 的 parameter_schema（实体属性表、克制矩阵、波次表、数值曲线）里，不靠堆更多是非题。下游 C3/C4 拆不动，根因是表太薄而非决策点太少。
- **确认负担 ≠ 决策点数量**：分两层——
  - **结构层（L0-L4）**：每个决策点逐条确认。高杠杆、需用户判断，一个不落。
  - **参数/数值表层（L5-L6）**：**以整张表为确认单元**。AI 提案整表值（每格挂 rationale/来源），用户确认"表结构 + AI 提案"为一个决策，并可**例外下钻**改任意行/格。一张 40 行属性表 = 1 次确认，不是 40 次。未下钻的格仍需用户对"整表提案"点确认（confirmed_by_user 覆盖整表），故不违背 #11——AI 仍未替用户提交，只是确认单元是表而非单元格。

决策点总量**不设硬上限**（原 §7 的 ≤120 已收回），按品类实际设计空间来；访谈时长由结构层决策点数量决定，与 L5/L6 表的行数无关。

### 3.4 品类包架构

- **通用层**：跨品类的决策点（节奏/视角/会话长度/经济骨架/难度哲学等）+ L0-L2 全部。
- **品类包 = 该品类的通用选项空间**（可插拔）：L3-L6 的品类专属决策点与选项（塔防的克制矩阵结构、战棋的移动/地形规则等），按品类的**设计空间**枚举——不是照抄某一款游戏的功能清单。以及该品类的**基数期望表**（合理的实体数量区间、资产数量区间——供流水线 C3 的基数门禁引用）。
- **≥3 款参考游戏交叉验证**：每个品类包的选项空间与基数区间，用至少 3 款该品类的成熟游戏横向对照校准。只逆向 1 款会把选项和基数带偏成"那一款的形状"，破坏通用性。参考游戏是**校准来源**，不是品类包要复刻的目标。
- 首批品类包（用户已定）：**通道塔防**、**格子战棋**；第三个视扩展需要。R1-C0 宪章 / lane_defense / 火焰纹章等均降级为**参考素材之一**，不与品类包一对一绑定。
- 品类包有版本号；项目记录所用包版本，包升级不影响已冻结项目。

### 3.5 设计冻结门（进入流水线的唯一入口）

按顺序全部通过才可冻结：

1. **完整性 / 拆分就绪度**：深度档内所有适用决策点均有 confirmed 选择；L5/L6 表结构/行数据完整。**完备度门**按深度档机器判定"下游能否不发明就拆分"——选 L6 则每张属性表填满、每个矩阵格有值、每关波次齐；缺格即 blocked 并列出待填清单（不给默认值，遵 R2）。这是防止 C3/C4 因结构化细节不足而瞎编的准入闸。
2. **一致性**：requires/conflicts 图校验零违例；跨决策机器校验（品类包提供校验规则，如「克制矩阵行数 = 守卫种类数」）。
3. **换皮门**：所有 `provenance=template:*` 的选择中，skin_fields 参数必须已被修改（与模板原值逐字段比对）；全部产出文本过**参考名扫描**（词表 = 模板库所有 gameName + 别名，模板入库时登记）。命中即 block，列出位置。
4. **AI 红队评审**：AI 以对抗姿态找设计矛盾/不可实现点/体验断裂，最低工作量证明（见红线 R3）。发现项用户逐条处置（修改/接受风险）后方可通过。
5. **冻结**：决策集 + 品类包版本 + 深度档 → 规范化 JSON → 内容哈希 → 只读。此后修改走版本化变更（新冻结版本），不可原地改。

## 4. 模板体系

### 4.1 模板的定义

模板 = **一个知名成熟游戏在当前选项体系下的逆向答卷**，是品类选项空间里的**一个参考点**——用于校准品类包、预填/对照项目，**不是项目要复刻的目标**（品类包才是通用物，见 3.4）。逐决策点记录：该游戏选了哪个选项、参数是什么、依据什么来源。

```jsonc
TemplateAnswer {
  decision_id, option_id, parameters,
  evidence: [{ source_url, quote, source_type: official|wiki|datamine|inference, confidence: high|med|low }],
  notes                              // 逆向者备注（如"官方未公开，按社区测定"）
}
Template {
  game_name, aliases: [...],         // 换皮门扫描词表来源
  genre_pack, pack_version, depth_reached,   // 逆向到哪层
  answers: [TemplateAnswer],
  coverage_report,                   // 各层覆盖率 + 低置信度清单
  certification: { reviewed_by, date, status }
}
```

原则：
- 只逆向**官方标准版玩法**，不收玩家自制/模组内容。
- 数值层（L6）允许用社区测定数据（wiki/datamine），但 source_type 与 confidence 必须如实标注；查不到的就空着并进 coverage_report——**宁缺勿造**。
- 模板深度可以低于 L6；用它开局的项目若选了更深的深度档，缺口由用户/AI 访谈补。

### 4.2 内置逆向工具链（模板生产线）

独立于项目流程的维护工具，产线：

1. **检索（混合 D 通道）**：官方/wiki 概览层由**带联网的检索通道自动拉取**（CLI 自带 WebSearch 或专用搜索 API），返回带 URL 的候选证据；低置信度条目与 L6 数值层走**人工供证**（人收集 datamine/wiki 来源贴入界面）。检索目标是**横向覆盖 ≥3 款同品类游戏**以描出选项空间边界，而非深挖单一游戏。
2. **填答**：AI 把证据映射到选项 + 参数，每条挂 evidence（source_url 必填）
3. **交叉核验**：第二个独立 AI 会话对低置信度条目复核（不同来源相互印证）
4. **人工审核**：审核界面逐领域过卷，可改可退回；**未经人工审核的模板不能入库**
5. **认证入库**：登记 game_name + aliases 进换皮扫描词表；产出 coverage_report

> 检索通道决策（Q5 = 混合 D）：现有 adapter（Codex/Claude CLI + OpenAI + imagegen）无可留证的联网路径。混合 D = 自动检索（官方/wiki 广度）+ 人工供证（低置信/数值层），既满足"宁缺勿造"红线，又契合"多游戏横向调研"的新目标。具体自动通道（复用带联网 CLI vs 专用搜索 API/MCP）在工具链落地时二选一，接口按"返回带 source_url 的结构化证据"设计以便替换。

### 4.3 模板进入项目

- **预填模式**：模板答案整卷预填进决策工具，每条 provenance=template:<id>；用户/AI 访谈在其上修改。冻结门的换皮检查兜底。
- **对照模式**：模板不进入项目，仅在决策点侧栏显示「该游戏此处的选择与理由」。
- UI 上两种模式均可用；预填模式在项目创建时明确警示「冻结前必须完成换皮」。

## 5. 开发流水线（完全重构）

### 5.1 总原则

- **输入唯一**：Phase 1 的唯一输入是冻结决策集编译出的 GameSpec。不再有 source_artifacts 概念包解析——概念文档只服务于设计阶段的 AI 访谈。
- **产物双格式**：每步产出机器契约（真相源，进哈希）+ 由契约渲染的人读文档（Markdown，不可手改，改了下次渲染覆盖）。
- **AI 分工**：确定性派生（编译/校验/渲染骨架）不用 AI；叙述性加工与评审必须用 AI，AI 不可用即 blocked。AI 产出必须锚定 GameSpec 路径（见红线 R4）。
- **步骤自治 + 单一职责**：每步一个职责、一组契约、一个门禁。

### 5.2 Phase 1：文档编译（C0-C6）

| 步 | 职责 | 关键产出（契约） | 门禁 | AI |
|----|------|-----------------|------|-----|
| C0 | 规格编译 | GameSpec（决策集规范化+哈希+索引） | schema 校验、决策集哈希绑定 | 无 |
| C1 | 静态验证与红队 | validation_report、redteam_findings | 机器规则零违例；红队最低工作量证明；发现项处置记录 | 必需 |
| C2 | 玩法设计文档 | gameplay_doc_contract（章节→spec 路径锚定表）+ 渲染 MD | 锚定覆盖率 100%（每个设计声明可追溯到决策）；无锚定叙述即 fail | 必需（叙述） |
| C3 | 内容与资产需求 | content_inventory、asset_spec_set（图/音/UI 分类，含生图用风格字段与画面描述）、audio_spec、ui_spec | **视觉形态白名单**（只有声明了视觉形态的实体才产美术资产；未知类型→blocked）；**基数门禁**（对照品类包基数期望表，超界→人工确认） | 必需（画面描述） |
| C4 | 程序需求与架构 | capability_contracts（接口/数据结构/验收场景 GWT，从 L4 机制规则派生）、unity_architecture（场景/Prefab/asmdef 划分） | 每能力≥1 可判定验收场景；机制规则覆盖率核对（L4 每条规则至少映射到一个能力） | 必需（接口设计） |

| C6 | 开发计划 + Phase1 签收 | task_graph（程序/资产/装配任务，依赖与并行分组）、phase1_signoff | 任务图与 C3/C4 全量对账；**人工门**：用户签收文档集 | 计划叙述 |

### 5.4 防复发红线（全流水线硬约束）

- **R1 指标即测量**：任何报告中的分数/计数必须携带证据指针列表（文件+路径+值）；证据为空而指标非零 → 步骤 fail。禁止任何硬编码指标字面量。
- **R2 未知即停**：派生规则遇到未知类型/无法分类的输入，产出 blocked + 待分类清单，**绝不给默认值**（禁止「认不出→art_asset/2048/P0」式 fail-open）。
- **R3 评审最低工作量证明**：评审类步骤必须：reviewed_count = 上游实际条目数（或显式声明抽样清单）；各评审报告内容哈希互不相同；零发现时必须逐类别给出「查过什么、为什么没问题」的证据指针。
- **R4 AI 产出锚定**：AI 生成的每段叙述/每个设计声明必须锚定到 GameSpec 决策路径；无锚定内容视为 AI 发明设计，fail。
- **R5 参考名扫描全程在线**：换皮词表扫描不只在冻结门，Phase 1/2 每步产物都扫（成本极低），命中即 block。
- **R6 基数申报**：任何一对多派生（实体→资产、机制→需求）必须声明映射规则与丢弃清单；产出数量对照品类包期望区间，超界必须人工确认。
- **R7 fallback 禁令**：全系统不存在「AI 失败→模板兜底→报 success」路径。AI 失败 = blocked + 明确原因。
