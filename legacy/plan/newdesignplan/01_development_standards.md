# 开发注意事项与开发标准

适用范围：`plan/newdesignplan/` 计划下的全部原子任务。
本文档是**强制标准**，与总计划 `00_master_plan.md` 第 10.1 节的冻结原则同级；原子任务文档不得与本文冲突，冲突时以本文和总计划为准并先修订文档。

---

## 1. 原子任务执行纪律

1. **严格按任务图顺序推进**；并行轨道（R1-C0、R0）只允许与其声明的并行区间重叠。
2. **每个原子任务独立提交**，提交信息说明任务编号；不满足本任务停止门不得启动依赖它的后续任务。
3. **禁止占位实现冒充完成**。用未验证的 stub、空实现、`todo!()` 通过验收即视为伪造证据（参照总计划 6.3：直接失败）。
4. 每个任务文档必须含：状态、依赖、目标、变更、验收、回滚边界。**回滚边界必须是删除式的**——回滚 = 删除新增物，不触及既有运行路径。
5. 任务做完更新任务文档的"状态"和"实际结果"两节；实际结果只写已验证的事实，不写意图。

## 2. 每次提交的最低门禁

Rust 侧（NEWrust 仓库内）：

```
cargo fmt --all -- --check
cargo check --workspace --locked
受影响 crate 的 cargo test --locked
安全自检（security-scan-allowlist 扫描）
```

触及 Web 层时追加：Web 单元测试、i18n 键完整性、设计内容门禁、UI 门禁（截图基线）。
触及流水线执行器或打包时追加：独立性边界扫描（0 父项目 Python 引用）、EXE smoke。

## 3. 架构红线（违反即打回，无例外）

1. **单写者**：任何代码路径不得绕过 `SpecStore`（规格域）或串行合入者（代码域）写权威状态。人工、模板、迁移器、AI 同一入口。
2. **AI 边界**：AI 只产出候选（`CandidateSpecPatch` / 代码域变更集）；禁止 AI 判定自己通过、跳过步骤、AI 投票、角色互审、用第二次 AI 调用替代确定性验证。
3. **依赖方向**：应用层 → 设计/流水线 → GameSpec → 基础库。`adm-new-game-spec` 不依赖 `adm-new-contracts`、UI、AI、流水线或具体引擎。DTO 只做显式转换或只读视图，不复制领域行为。
4. **核心词汇**：核心类型与编译器分支不得出现品牌名、引擎名、游戏类型名。类型标签只能用于检索与展示。
5. **可迁移性**：机器路径、AI 凭证、API 费用、并发参数不进入可迁移规格和审计日志（属 ExecutionBudget / 本机绑定层）。审计记录不含密钥、认证头或未脱敏原始提示。
6. **确定性**：投影和编译器是纯函数或显式 IO；同一输入 + 同一版本 = 同一语义结果。带随机性的组件（LLM/VLM）的输出只能作为证据或候选，其结果必须按输入内容哈希缓存以保证可回放。
7. **fail closed**：缺输入、未知引用、schema 不匹配一律阻塞，禁止静默降级、空模板成功、"文件存在即通过"。

## 4. 反过拟合标准（持续执行，不是一次性验收）

1. **第一层**（已有，保持）：核心词汇黑名单扫描 + crate 依赖方向测试 + `deny_unknown_fields`。
2. **第二层**（A03 起每个编译器任务强制）：任务验收必须包含
   - 标签置换测试：样例类型标签替换为无意义字符串后，编译输出语义不变；
   - 能力扰动测试：改变一个能力谓词，输出必须相应变化。
3. **第三层**（A09）：八类规格级全覆盖 + mutation + N=20 重复 + 无 AI + 故障注入。
4. **字段晋升规则**：字段进核心前必须被 ≥3 个结构明显不同的样例共同需要；否则进 `ExtensionBlock`。评审新增核心字段时在 PR/提交说明中列出三个样例依据。
5. R1 允许 Step07–14 实现对通道防守做深，但上述测试不得豁免。

## 5. 数据与序列化标准

1. JSON 契约统一严格 camelCase + `deny_unknown_fields`；未知扩展进命名空间 `ExtensionBlock`，禁止散落 `flatten Value`。
2. 实体 ID 使用受验证新类型；无序集合用 `BTreeMap` 或规范化排序；**有序语义序列（步骤、效果栈、对话分支、状态迁移列表）保持输入顺序**，不得为哈希稳定而排序。
3. 内容哈希包含 schema 版本、修订号、父修订哈希和全部语义内容（含 ProductEnvelope），不含自身哈希字段。
4. 错误必须含稳定代码、严重级别、规范路径、相关 ID 和修复提示。

## 6. 测试标准

1. 新增验证逻辑必须配 **mutation tests**：删除引用、重复 ID、无效迁移、空效果、断裂追踪等无效样例必须失败。只测 happy path 不算完成。
2. 涉及 AI 的功能必须测试：越界路径、提示注入、无效 JSON、陈旧补丁、超时、重试、**关闭 AI 模式**。
3. 涉及执行器的功能必须测试：越界写入拒绝、失败分类正确、软停止、断点续跑。
4. 受信测试（任务合同中的验收检查）**不可由编码代理修改**；执行器必须以基线树哈希验证受信测试未被篡改。
5. 确定性回归：同一冻结规格重复执行，比对语义哈希。

## 7. 质量评分与证据标准

1. 每步评分由可复算指标构成（契约完整 25 / 追踪闭合 20 / 矛盾不变量 20 / 场景覆盖 20 / 定制与证据 15）；阻塞错误封顶 69。
2. 静默 fallback、未知引用、未确认高风险 AI 写入、伪造证据 = 直接失败。
3. AI 调用证据：非敏感模型配置 ID、输入/输出摘要哈希、验证结果、用户确认记录。
4. 报告如实：测试失败要写明输出；跳过的步骤要标注；不得把 skipped 呈现为 passed（`skipped_with_warning` 一类状态不得计入通过率）。

## 8. 人工确认标准

1. 确认策略是数据（项目级配置：`attended` / `unattended` / `sample(n)` / `auto_accept`），不是散落在代码里的 if。
2. 默认策略见总计划 7.2；变更默认策略是产品决策，需用户确认。
3. `auto_accept` 必须显式配置且留审计；"批量确认"是人工模式，不是无人值守。
4. 对外正式发布签署永远人工。

## 9. 兼容与迁移标准

1. `game_spec_v2` 是项目级持久开关；环境变量只用于开发测试。
2. 双轨期间不反向覆盖旧状态；差异报告是产物不是日志。
3. 迁移必须有预览、备份、回滚和幂等测试；迁移失败不得改变原保存。
4. 现有三套执行实现（`work_unit.rs` / `adm-new-patch` / `execution_objects.rs`）在 A08c 迁移前保持可用，不得提前废弃。

## 10. 文档同步标准

1. 设计决策变更先改 `plan/newdesignplan/` 文档，再改代码。
2. 每个原子任务完成后同步跨会话记忆（按 CLAUDE.md 记忆同步规则）。
3. 计划文档中的代码引用必须给出文件路径（可含行号），且引用时必须真实存在——引用失效按文档 bug 处理。
