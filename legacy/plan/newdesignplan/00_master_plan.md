## 0. 与 v1 计划的关系

v1 计划把系统定位为"通用游戏规格编译器"，其领域模型、确定性验证、单写者、AI 边界四大方向经复核全部保留。v2 重写的原因是 v1 存在结构性缺陷：

1. **头重脚轻**：A08 用 20 行覆盖 Step07–14，而这是"能否产出可玩游戏"的 80% 工作量所在。
2. **风险后置**：直到 A08 末尾，系统一次完整游戏都没产出过；Step11 代码执行、Unity 打包等致命风险要到投入 A01–A07 全部成本后才暴露。
3. **产品未定义**：整个任务图都在设计"工厂"，没有一份文档定义"产品"——通道防守游戏做成什么样才算数。
4. **反过拟合防线被高估**：A01 的实际测试只是禁止词黑名单 + 依赖方向检查（`anti_overfit.rs`），"三样例晋升规则"没有机器强制；即使核心类型干净，A03/A07/A08 的编译器仍可能硬编码单一品类逻辑。
5. **忽视存量代码**：Rust 侧已有隔离工作单元（`work_unit.rs`：声明输出、越界拒绝、前后哈希）、独立补丁执行器（`adm-new-patch`：`CodexPatchRunner`）、无人值守恢复配置（`execution_objects.rs`：`UnattendedExecutionConfig`）三套相关实现，重新设计第三套补丁系统会制造返工。

v2 的核心转变：**从"编译器计划"转为"先证明能造游戏，再扩展通用性"的计划。**

## 1. 系统定位

不是对旧流水线的局部修补，而是把 Rust 版本重构成一个自动游戏开发系统：

```
用户意图 → GameSpec → 确定性编译 → 代码/资产生产 → 测试 → 可执行游戏
```

### 1.1 六大架构原则（继承 v1，全部冻结）

1. **GameSpec 是唯一权威状态**。游戏意图、实体、动作、状态、资源、场景、资产和技术约束全部进入类型化规格。
2. **按能力组合，不按类型硬编码**。系统读取空间、时间、控制、参与者、内容、联网等能力轴；"塔防""卡牌"等标签只用于检索，不选择逻辑。
3. **单写者机制**。用户、模板和 AI 都只能提交 `SpecPatch`，经验证后由唯一的 `SpecStore` 提交，生成新修订和不可变审计记录。
4. **AI 不直接控制项目**。AI 只生成候选补丁（`CandidateSpecPatch`），不能自行宣布通过、跳过步骤或覆盖权威状态。禁止 AI 投票、角色互审、AI 自主选择流程。
5. **D1–D4 和 Step00–14 外壳保持不变**。保留用户熟悉的界面和步骤编号，重定义每步的输入、输出和质量门禁。
6. **渐进式替换**。项目级 `game_spec_v2` 开关（默认关闭）、影子生成、差异报告；不一次性破坏旧项目。

### 1.2 不做的事情

1. 不重新引入 CrewAI、多角色互审、AI 投票或 AI 自主选择流程。
2. 不允许 AI 直接写权威状态、判定自己通过、跳过验证或静默降级。
3. 不在第一阶段一次性替换现有 `ProjectState`、保存格式和流水线。
4. 不把 Unity、塔防、卡牌、叙事等引擎或类型专属概念放入通用核心。
5. 不在没有真实数据时冻结精确数量指标（见 4.1 包络分档）。

## 2. 两阶段发布：R1 垂直切片 → R2 通用生产系统

### 2.1 R1「可玩游戏垂直切片」

一个品类（通道防守）从 D1 走到 Step14，产出**内容完整、玩法闭环成立**的可双击运行 EXE。

选择通道防守的理由：PvZ 验证样例、素材经验、旧 Python 流水线 Step07/Step11 的实战数据都在这条线上，校准成本最低。

**R1 停止门不是"生成可运行 EXE"**——"能跑"和"是个游戏"之间隔着全部内容质量。R1 停止门 = R1-C0 内容宪章定义的全部验收场景通过 + 玩法闭环成立（见 2.4）。

R1 阶段允许 Step07–14 的实现只对通道防守做深，但核心类型与编译器持续受反过拟合门禁约束（见 5）——过拟合防线在类型层和编译器测试层，不在"同时开发几个游戏"上，垂直做深不污染核心。

### 2.2 R2「通用生产系统」

横向扩展品类（分层验证矩阵）、无人值守模式扩展、旧项目迁移与 `game_spec_v2` 默认切换。

### 2.3 R0「技术探针」（并行轨道，非发布阶段）

在 A02/A03 进行的同时，用**手写的固定最小 GameSpec + 一次性占位内容**走通：

```
最小规格 → 现有内核生成少量代码和一个场景 → Unity 批处理编译 → smoke → EXE
```

R0 的定位：
- **纯技术风险验证**：提前暴露 Step11 工具链、工作区提交、Unity 批处理、打包链路的致命问题，不等 A08 才发现。
- **不是游戏内容成果**：占位内容用完即弃，R0 的产物不得被当作 R1 的内容起点。
- **交付一个可重复运行的 harness**：探针代码可丢，harness 不能丢——它后续演化为 A08c 执行引擎的回归测试床。
- **是 A04 的前置**：R0 用现有三套实现真实跑一遍，暴露的失败分类、越界模式、批处理坑位是设计统一变更内核最需要的输入。先探针、后统一。

### 2.4 R1-C0「内容宪章」（最先启动，用户决策）

在一切编译器工作之前回答四个问题：

1. 要产出什么样的通道防守游戏。
2. 游戏完成到什么程度（波次规模、局外系统有无、音频层级等）。
3. 自动化与人工决策的边界。
4. 什么条件代表"真正可玩"和"验收通过"。

**交付物分两层，机器层是硬要求：**

- 人读层：游戏概念、范围、完成度定义、人工/自动边界表。
- 机器层：
  - 可玩标准直接写成 GameSpec 的 `AcceptanceScenario` 草稿（Given/When/Then）；
  - 完成度定义写成 `ProductEnvelope` 档位取值。

这份草稿是 A07 冻结规格 fixture 的种子，A08f 停止门的判定依据就是"这些场景全部通过"——从宪章到停止门一条线贯通，中间没有主观转译。

**决策主体是用户**。AI 准备带选项和成本估计的决策文档，用户拍板，结果落成宪章。R1-C0 不依赖任何代码任务，与 A02 并行：A02 交付包络的类型与哈希机制，宪章交付包络的具体取值，两边在 A02 末尾汇合。

## 3. 设计流程与流水线职责

### 3.1 D1–D4（外壳保留，内部重解释）

| 阶段 | 新职责 | 必须输出 |
|---|---|---|
| D1 | 项目意图、用户、平台和硬约束 | `ProjectIntent`、开放问题、不可违反约束 |
| D2 | 能力画像与动态决策图 | `CapabilityProfile`、激活模块、决策依赖 |
| D3 | 实体、动作、状态、资源、反馈和玩法闭环 | 玩法与内容规格合成 |
| D4 | 验收场景、追踪关系、风险和规格冻结 | 冻结哈希、追踪矩阵、未决风险 |

原 16 领域 / 103 节点 / 515 清单项降级为激活感知的知识库：只有命中能力谓词且对当前规格有未满足约束的节点才激活；未激活内容不拉低完成度。

D4 冻结的人工/自动策略：R1 默认人工冻结；R2 允许在**预先批准且签名的 ProductEnvelope 内**自动冻结（见 7.2）。

### 3.2 Step00–14（外壳保留，契约重建）

| 步骤 | 新职责 | 确定性门禁要点 |
|---|---|---|
| 00 | 输入快照与基线 | 身份、版本、完整输入、无隐式父目录依赖 |
| 01 | 意图与约束编译 | 体验承诺、范围、平台约束无矛盾 |
| 02 | 能力画像与决策图 | 激活理由完整、无类型名硬分支 |
| 03 | 动作与交互契约 | 每个核心循环可追踪到动作、条件、效果和反馈 |
| 04 | 世界、实体、状态和资源 | 引用有效、迁移闭合、资源约束可解释 |
| 05 | 验收场景与测试模型 | 每项关键承诺至少一个正向和失败场景 |
| 06 | GameSpec 冻结与交接 | 无阻塞问题、追踪闭合、冻结哈希稳定、**规格不超出 ProductEnvelope 即刻判定** |
| 07 | 美术规范、风格锚点与代表资产 | 只生产规范 + 锚点 + 少量代表资产；不批量生产（见 6.1） |

| 10 | 实现任务图 | 任务合同齐全：写入范围、机器可执行验收检查、依赖、回滚（见 6.2） |

| 12 | 批量资产生产、导入与运行时绑定 | 按冻结 AssetManifest 批量生成；真实引擎加载验证（见 6.1） |
| 13 | 玩法、性能、可访问性和回归测试 | 验收场景可执行化，证据闭合 |
| 14 | 打包与发布证据 | 可重现构建、完整性、EXE smoke、发布清单 |

UI 只展示当前步骤产物；图像等富媒体不泄漏到其他步骤视图。

## 4. 生产包络：两层拆分

### 4.1 ProductEnvelope（进 GameSpec、进哈希、可迁移）

描述**产品规模**：场景数档位、系统复杂度档位、资产规模档位、内容量档位。Step06 冻结时确定性判定"这个规格是否在本系统当前生产能力内"，超出即拒绝——不是跑到 Step11 才发现做不完。

**分档而非精确数字**：在 R0/R1 产出真实数据之前，任何"200 张图片 / 400 个任务"式的精确上限都是没有依据的猜测（旧项目 369 任务约 37 小时只能证明拆分过细，不能证明 400 合理）。R1 阶段用粗粒度序数档位（任务规模 S/M/L、资产规模档位）；R1 完成后用真实数据校准为加权复杂度预算；A09 才启用精确预算。**没有数据时不伪装精确。**

R1 包络方向性约束（档位值由 R1-C0 确定）：2D、单人、离线、authored 内容；网络协作品类在 R1 与 R2 首轮只做到"规格 + 架构编译通过"，不做完整生产。

### 4.2 ExecutionBudget（本机运行策略，不进规格）

API 费用、超时、重试次数、并发数属于本机执行策略，随 `UnattendedExecutionConfig` 一系管理，**不进入可迁移 GameSpec、不参与哈希**——与 v1 "机器路径和凭证不进入可迁移规格"是同一原则。

## 5. 反过拟合：三层防线（承认现状，持续加固)

**现状承认**：A01 的 `anti_overfit.rs` 只是 7 个禁止词黑名单 + crate 依赖方向检查，是第一层防线，不是完整防线。

1. **第一层（已有）**：核心词汇黑名单 + 依赖方向测试 + 严格 unknown-fields。
2. **第二层（每个编译器任务自带，不攒到 A09）**：从 A03 起，每个涉及编译器的原子任务验收标准必须包含：
   - **标签置换测试**：把样例的类型标签换成无意义字符串，编译输出语义不变；
   - **能力扰动测试**：改变一个能力谓词，输出必须相应变化。
3. **第三层（A09 全量）**：八类样例规格级编译全覆盖、字段 mutation、重复 AI N=20、无 AI 模式、故障注入、核心源码品牌扫描。

核心晋升规则保留：字段进入核心前必须被至少三个结构明显不同的样例共同需要，否则留在 `ExtensionBlock`。

## 6. 生产阶段关键设计（原则冻结，字段级细节按需设计）

以下各节冻结**原则**；接口字段、参数取值、缓存机制等实现细节延后到对应原子任务启动时、内容宪章确认之后再设计。延后是省力，不是失控——原则写进本计划即为冻结，后续任务不得偏离。

### 6.1 Step07 / Step12：资产生产职责拆分

- **Step07 只生产**：美术规范、风格锚点、少量代表资产（主角、核心 UI 等关键项）。风格锚点由人工确认，成为后续一致性比对的参考集（继承旧 Python 版已验证的手动风格确认模式）。
- **Step12 才批量生产**：在 Step09 冻结 `AssetManifest` 之后批量生成、导入、绑定。避免架构或任务图变化让大量图像作废。
- **资产质量两层门禁**：
  - 硬门禁（确定性）：解码、尺寸、alpha、切片几何、透明边距、重复图检测、OCR 水印、对比度、文件完整性。全部机器判定。
  - VLM 评审（证据，不是裁判）：VLM 输出结构化评分与差异描述，作为评审证据进入审计记录；**VLM + 固定阈值不构成确定性验证**（VLM 输出有随机性）。评审结果按图像内容哈希缓存，同一张图只评一次，重跑流水线不重新掷骰子——系统行为可回放。
  - 现有 `stage12.rs` 的"文件存在即通过"确认废弃重建。
- **Step12 集成定义 = 真实引擎加载**，不是文件复制到位：①每个资产至少被一个场景/预制体引用，孤儿资产 fail；②headless/smoke 运行时逐个实例化加载，失败 fail；③引用了但不存在的资产在 Step12 阻塞，不漏到 Step13。

### 6.2 Step11：受控代码执行（统一变更内核）

**核心思想：Step11 是 SpecPatch 模型在代码域的镜像。** 规格域和代码域共用"单写者 + 声明范围 + 审计"一个心智模型。

**不新建第三套补丁系统。** 现有三处实现——`work_unit.rs`（隔离工作单元、声明输出、越界拒绝、前后哈希）、`adm-new-patch`（`CodexPatchRunner`）、`execution_objects.rs`（`UnattendedExecutionConfig`：修复上限、失败分类、独立任务继续）——统一为共享的 **ChangeKernel**（事务/审计/并发内核）+ **WorkspaceChangeSet**（代码域变更集合同）。

**分两步防止大爆炸重构**：
- A04 只交付：ChangeKernel 抽象层 + `SpecStore` 作为第一个实现 + `WorkspaceChangeSet` 的**接口与合同定义**（合同必须覆盖：读取集合、写入集合、删除/重命名、二进制文件、基础树哈希、命令权限、资源预算、**受信测试不可由编码代理修改**）。
- A08c 才迁移：现有三套实现向 `WorkspaceChangeSet` 实际迁移。届时 R0 harness 已存在，迁移有回归保护；流水线重构本来就要动这些代码，一次动而不是两次。

**执行循环原则**：
1. 任务合同（Step10 产出）：声明写入路径集合 + 机器可执行的验收检查（编译目标 + 任务专属受信测试，Step10 生成，不靠 Step11 的 AI 自证）+ 依赖。
2. 隔离生成：每任务在独立工作副本中由编码代理（复用现有 adapter 层）执行，产出变更集。
3. 确定性验证：越界写入直接拒绝（不是警告）；编译/测试失败进入修复循环。
4. 有界修复：失败证据（编译输出、测试输出、越界清单）结构化回喂，重试有上限；失败分类显式（compile / test / scope_violation / timeout / agent_error），scope_violation 不重试同一提示，缩小任务或升级人工。
5. 修正队列（停车场）：预算耗尽的任务入队，流水线在 DAG 无关分支继续（继承旧项目 Step11/12 无人值守恢复的实战教训）。Step11 成功判定 = 停车场为空或全部人工解决。
6. **并行生成、串行合入**：执行器从第一天支持并发模型，但 R0/R1 默认 `max_workers=1`；变更集可并行生成，必须由单写者串行合入——每次集成失败都有唯一责任任务，无需组级二分。
7. 每次合入后跑构建 + smoke；支持软停止 + 断点续跑。

具体并发数、重试次数、调度策略属于 ExecutionBudget 参数，延后到 A08c 按 R0 数据设计。

### 6.3 质量评分体系

不使用"AI 自评分"作为发布结论。每步 100 分由可复算指标组成：契约完整度 25 / 引用与追踪闭合 20 / 矛盾与不变量 20 / 验收场景覆盖 20 / 项目定制与证据质量 15。存在阻塞错误总分封顶 69；存在静默 fallback、未知引用、未确认高风险 AI 写入或伪造证据直接失败。主观体验评价只作附加评审，不覆盖确定性门禁。

## 7. 人工确认与无人值守

### 7.1 原则

**机器负责可验证的，人负责不可逆的和品味性的。** 确认策略数据化：每个门禁一个项目级策略字段（`attended` / `unattended` / `sample(n)` / `auto_accept`），低风险补丁"批量确认"仍是人工模式，真正无人值守必须显式 `auto_accept`。

### 7.2 默认策略（R1）

| 必须人工 | 可无人值守 |
|---|---|
| R1-C0 内容宪章决策 | Step08–10 编译（本身确定性） |
| D4 规格冻结（R1 默认；R2 可在预批准签名包络内自动） | Step12 批量资产（硬门禁全检 + 抽样人工确认） |
| Step07 风格锚点批准 | 低风险 AI 补丁（显式 auto_accept 策略下） |

### 7.3 硬要求

1. 所有无人值守路径必须可回放、有审计记录（复用 A05 证据模型：模型配置 ID、输入/输出摘要哈希、验证结果、确认记录；不记录密钥、认证头或未脱敏原始提示）。
2. 无人值守运行支持软停止 + 断点续跑。

## 8. 验证矩阵：分层，不八类全量

反过拟合防线的真正来源是字段晋升规则、持续编译器门禁和**规格级编译全覆盖**——规格级编译（D1–Step10，不执行 Step11–14）已足以暴露"核心被单一品类塑形"，而八类全生产意味着八份资产预算 + 八轮 Step11 成本，边际收益递减。

- **Tier 1（随 R1）**：通道防守全生产；三消 / 分支叙事 / 回合战术（复用 A01 样例）规格级编译。
- **Tier 2（R2 主体）**：再选 **3 类**全生产。**具体选择哪三类，等 R1 完成后按实际暴露的能力缺口决定**——现在选是没有信息的猜测。选择标准：能力距离最远优先。
- **Tier 3**：其余品类规格级 + 关键步骤抽查；网络协作只做规格 + 架构验证。

A09 保留：标签置换、字段 mutation、重复 AI N=20、无 AI 模式、故障注入、核心源码品牌扫描。

1. `game_spec_v2` 项目级开关默认关闭，先双轨生成不接管 UI；环境变量只用于开发测试。

## 11. 完成定义

**R1 完成**：
1. 通道防守项目从空状态完成 D1–D4 和 Step00–14，产出内容完整、验收场景全通过的可玩 EXE。
2. 无隐式读取旧项目或父目录数据；便携验证与 EXE smoke 通过。
3. AI 补全在产物中有明确使用证据；关闭 AI 时流程仍可人工完成。
4. 核心源码无品牌名或类型专属默认分支（三层防线全部通过）。

**R2 完成**：
5. 八类样例通过规格级 schema、引用、不变量、场景、追踪和重复性门禁；选定的 3 类全生产达标。
6. 旧项目可读取、迁移、回滚；迁移失败不损坏原保存。
7. `game_spec_v2` 默认开启；角色化 AI 路径和类型硬编码删除（保留兼容读取窗口）。
