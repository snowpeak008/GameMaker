# 开发流水线步骤 N-M 输入、分阶段暂停、断点续跑与断点重连修复计划

## 状态

已完成（2026-07-11）：自然步骤输入、canonical range、后台执行、停止边界、run/attempt、CAS checkpoint、Step07/11/12 安全工作单元、显式恢复/重新核验和重启投影均已实现并有 Rust/Web 回归测试。原状态描述保留为历史背景。

## 问题

开发流水线的“步骤 N-步骤 M 顺序执行”需要与 Python 项目的使用方式保持一致：

1. 起始步骤和结束步骤填写步骤 ID。用户输入 `1` 时按 `01` 步骤处理，输入 `8` 时按 `08` 步骤处理，输入 `12` 时按 `12` 步骤处理；输入 `00` 也应继续表示 `00`。
2. 点击运行后立即开始后台执行，界面不能被同步执行阻塞。
3. 点击停止后，应在当前小阶段/安全执行单元完成后暂停，而不是只能等整个流程或整个长步骤结束。
4. 下次继续运行同一范围或同一步骤时，应从上次已完成的下一个安全执行单元继续，已成功完成的单元不能重复执行。
5. 应支持应用关闭、界面刷新、IPC/前端重连后的断点恢复；恢复前需要让用户明确点击“继续/恢复”，不能静默重复执行或静默续跑。

当前 Rust 版本只实现了其中一部分，不能宣称已经完成 Python 对照功能。

## 复现条件与期望结果

### 正常范围运行

- 在起始步骤输入 `1`、结束步骤输入 `8`，期望后台按 `01, 02, ..., 08` 的注册拓扑顺序执行。
- 在起始步骤输入 `8`、结束步骤输入 `12`，期望按 `08, 09, ..., 12` 执行。
- 点击“运行”后，命令应立即返回运行已受理/运行中的状态，流水线实际工作在后台执行。
- 不允许因为前端显示补零而要求用户手动输入 `01`、`08`。

### 安全停止与继续

- 在一个包含多个任务、分组或其他可安全提交单元的长步骤执行期间点击“停止”。
- 当前正在执行的单元完成或到达该单元允许的安全边界后，持久化停止状态和断点，后续单元不再启动。
- 点击“继续/恢复”后，从断点记录的 `next_unit_id` 或等价游标继续，已完成单元只复用结果，不重新生成、不重复写入副作用。

### 断点重连

- 停止后关闭应用并重新打开，或刷新前端/重新建立 IPC 连接。
- 流水线详情应显示“可恢复”以及步骤、单元、停止原因和断点时间。
- 用户明确选择继续后恢复原运行；如果项目、配置、草稿或执行版本已经不匹配，应阻止恢复并明确提示只能重新运行该步骤或重新建立断点。

## Python 对照基线

Python 项目中的行为以现有实现为对照，不修改 Python 代码：

- `core/ui/pipeline_panel.py` 使用 `tk.IntVar` 和 `tk.Spinbox` 保存范围，因此输入 `1`、`8`、`12` 传入执行层时已经是整数，而不是必须手动补零的字符串。`_exec_range` 在后台线程调用 `core.main.run_range`，所以运行是立即受理、异步执行。
- 同一文件的“停止”按钮调用 `core.runtime.control.request_stop`，运行器在阶段/执行单元边界检查停止请求。
- `core/runtime/control.py` 持久化停止请求和当前运行状态，包含运行 ID、停止边界和处理状态。
- `core/engines/generation.py` 对开发执行长阶段保存任务记录和阶段检查点；`core/engines/execution_objects/unattended_recovery.py` 的 `build_resume_cursor`、`write_pause_resume_log` 明确记录当前任务、下一任务、分组、恢复策略，并要求复用已成功任务、从下一未完成任务恢复。
- `core/main.py` 的通用 `--resume` 主要服务 prepared iteration delta plan，不能直接当作“开发流水线 N-M 范围的通用断点续跑”实现；Rust 需要把流水线运行断点单独建模。

## 核查结论

### 已实现

- Rust 已有步骤注册表和拓扑顺序；当前默认注册表可以执行 `00` 至 `14` 的范围。
- Rust 已有起始步骤/结束步骤范围执行入口。
- Tauri 通过后台任务执行范围运行，运行按钮不是同步阻塞式调用。
- Rust 有停止状态和停止请求的初步持久化。

### 未实现或实现不完整

1. **步骤 ID 的输入语义未对齐 Python。** 当前前端只能选择已有的补零字符串，后端仍按字符串精确匹配；没有在共享边界把 `1` 规范化为 `01`、把 `8` 规范化为 `08`。
2. **“完成一个小阶段后暂停”未实现为通用能力。** 当前停止主要发生在下一个步骤开始前；步骤执行器没有安全单元回调、实时停止检查或检查点提交协议。
3. **“下次继续当前步骤”未实现。** Rust 运行状态没有当前/下一个安全执行单元，也没有“已完成单元可复用”的恢复记录。
4. **“断点重连”未实现。** 应用重启目前只把 `running` 收敛成 `stopped`，重连后没有可恢复状态和用户操作。
5. **停止请求存在状态同步风险。** 后台执行使用克隆的 `PipelineRunState`，停止命令更新的是运行时状态和原持久化状态；仅由 `StopAwareExecutor` 的原子标记在步骤开始时读取。尤其在最后一步或停止请求与步骤完成竞态时，可能出现停止请求被最终完成状态覆盖，或停止只能等整个步骤调用返回。

因此，本问题应按“功能缺失 + 停止竞态/恢复一致性风险”处理，而不是只改输入框。

## 根因

### 1. 输入边界没有统一的步骤 ID 解析器

前端 `pipeline.js` 直接把选择值转为 `from_stage_id`/`to_stage_id`，流程服务再用字符串查找注册表。该设计把展示格式误当成领域输入格式，无法复现 Python `IntVar` 带来的数字输入行为，也无法保证 CLI、Web、Tauri 入口一致。

### 2. 步骤执行接口是“一步一次”，缺少安全执行单元

`ProductPipelineExecutor::execute_step` 将一个步骤直接交给生成服务完成，`StageExecutor` 接口没有执行上下文、停止令牌、单元完成回调或检查点存储。因此上层只能在步骤调用前后控制，无法在长步骤内部实现“完成一个小阶段后停止”。

### 3. 停止信号和工作状态不是同一个实时来源

Tauri 运行器一侧有 `Arc<AtomicBool>`，流程服务一侧又有复制出来的 `PipelineRunState.stop_requested`。后台任务拿到的是克隆状态，停止命令更新的状态不一定会被当前工作任务看到；执行完成后再用克隆状态覆盖运行时状态，会放大竞态。

### 4. 持久化模型没有记录可恢复游标和一致性依据

现有 `PipelineRunState` 只能表达“当前步骤正在运行/已停止/已完成”，不能表达“步骤 08 已完成到任务 T17，下一次从 T18 开始”。也没有保存范围、项目/草稿身份、配置版本或执行计划指纹，无法判断断点是否仍然适用。

### 5. 重启逻辑只做状态清理，没有恢复协议

`runtime.rs` 将中断的 `running` 状态改为 `stopped`，但未保留或暴露恢复游标，也没有显式 resume command、恢复前校验和恢复后的幂等策略。

## 修复方案

以下顺序是实施计划，不是本次已经执行的代码修改。

### P0：统一步骤输入与范围语义

1. 在 Rust 共享领域/命令边界新增唯一的步骤 ID 解析和规范化逻辑，前端只能负责展示和提示，不能成为唯一校验点。
2. 解析规则：
   - 先去除首尾空白；
   - 只接受十进制整数文本，例如 `0`、`00`、`1`、`8`、`12`；
   - 转为数字后按注册表有效范围校验；
   - 再按注册表的 canonical ID 格式生成 `00`、`01`、`08`、`12`；
   - 拒绝空值、负数、小数、字母、超出注册表的步骤和无法解析的值；
   - 起始和结束步骤按注册表拓扑位置校验，不允许反向范围。
3. `RunPipelineRangeRequest` 在进入 service 前完成规范化，并让后续日志、持久化状态、响应和恢复记录都只保存 canonical ID。
4. Web 将当前两个下拉框改成可编辑的步骤 ID 输入（可保留合法步骤提示/下拉辅助），至少支持直接键入 `1`、`8`、`12`；提交失败时显示明确错误，提交成功后回显 `01`、`08`、`12`。
5. 保留已有拓扑排序作为真正执行顺序，不使用字符串排序替代注册表顺序。

### P0：修复停止信号和运行状态一致性

1. 为每次范围运行建立唯一的 active run context，停止命令和后台任务共享同一个可取消信号/停止请求源；不能依赖后台任务中一次性克隆的 `stop_requested` 字段。
2. 停止请求必须带 `run_id`、请求时间、停止模式和目标安全边界，并持久化为“已请求、处理中、已在边界停止或已完成”的可追踪状态。
3. 后台任务在以下位置读取实时停止信号：
   - 新步骤启动前；
   - 长步骤的每个安全执行单元开始前；
   - 安全执行单元提交后；
   - 步骤完成准备写入最终状态前。
4. 停止请求到达最后一个步骤时，如果运行尚未明确完成，必须先保存停止结果和检查点，不能由最终成功状态覆盖；只有所有范围步骤和所有单元都已成功提交后才清除可恢复停止状态。
5. 处理“停止命令在步骤完成同时到达”的竞态：使用 run ID/状态版本或等价的 compare-and-set 规则，保证最终状态与实际已提交的检查点一致。

### P0：建立安全执行单元和检查点协议

1. 扩展 Rust 执行接口，明确 `StageUnit`/`ExecutionUnit` 的最小生命周期：开始、执行、成功提交、停止边界、失败；每个可恢复单元必须具有稳定 ID。
2. 对本身不可拆分的短步骤，安全单元可暂时等同于整个步骤，停止语义明确为“当前步骤完成后停止”。
3. 对照 Python 的长执行阶段，优先把开发执行中的任务/分组作为安全单元；至少覆盖当前需要支持断点继续的 Step11/Step12 路径。每完成一个任务/分组：
   - 先写入该单元的成功结果和副作用记录；
   - 再原子写入 checkpoint；
   - 最后检查停止请求并决定是否结束运行。
4. 检查点至少包含：
   - `checkpoint_version`；
   - `run_id`、canonical `from_stage_id`/`to_stage_id`；
   - 项目、当前草稿/存档和执行计划身份；
   - 当前步骤 ID、当前单元 ID、`next_unit_id`；
   - 已完成单元及其结果/产物引用；
   - 停止原因、停止边界、创建时间和更新时间；
   - 输入/配置/代码或执行计划指纹；
   - `resume_policy` 和是否允许自动复用已成功单元。
5. 检查点写入使用现有安全持久化约定（临时文件、完整写入、原子替换、可读校验）；不能只在内存里保存，也不能用最终步骤结果文件推测执行进度。
6. 将“产物中有 `resume_supported` 字段”与“运行器真的支持 resume”区分开；只有检查点、恢复命令和幂等执行都接通后，才向 UI 暴露可恢复能力。

### P1：实现显式继续/断点恢复

1. 增加明确的恢复命令或等价的 `resume` 模式，不复用普通“运行”命令的隐式行为。请求至少包含 `run_id`/checkpoint ID，并由后端重新加载 canonical 范围。
2. 恢复时校验：
   - checkpoint 状态是 `stopped`/`recoverable`，而不是已经成功完成或仍由其他 worker 占用；
   - 项目和当前草稿/存档身份一致；
   - 执行计划、配置、版本和必要输入指纹一致；
   - checkpoint 版本受当前程序支持；
   - 已完成单元的结果和产物仍可验证。
3. 校验通过后，从 `next_unit_id` 开始执行，已成功单元直接复用；恢复后的新运行仍沿用原 `run_id` 或建立可追踪的续跑 ID，但必须保留父检查点关系。
4. 校验失败时不得强制续跑；返回不可恢复原因，并提供“重新运行当前步骤/重新开始范围”的明确路径。
5. 应用启动、前端刷新和 IPC 重连只负责加载并展示 `recoverable` 状态，不自动执行恢复；用户点击“继续/恢复”后才启动后台任务。
6. 完成全部范围后归档或清理活动 checkpoint，但保留足够的运行审计记录，避免下一次普通运行误识别为可恢复运行。

### P1：补齐 Web 交互和状态展示

1. 范围区域显示可编辑的起始/结束步骤 ID和规范化后的 canonical 值。
2. 运行中：禁用新的冲突运行和范围编辑，启用“停止”，显示当前步骤、当前安全单元以及停止请求是否已受理。
3. 已安全停止且存在有效 checkpoint：显示“继续/恢复”，并显示“从步骤 X / 单元 Y 继续”。
4. 已中断但 checkpoint 校验失败：显示不可恢复原因，并提供重新运行当前步骤的操作，不显示误导性的“可恢复”。
5. 运行完成、失败、停止和等待人工确认的状态要与已有 Step07 风格确认状态区分，不能把“停止请求已发出”误显示成“已完成”。
6. 所有新增按钮、错误、停止原因和恢复提示补齐中英文文案及可访问性标签。

## 测试与验收

### 领域与 Rust 单元测试

- 步骤规范化：`1 -> 01`、`8 -> 08`、`12 -> 12`、`00 -> 00`，并覆盖空白、负数、小数、字母、超范围、反向范围。
- 范围顺序：输入 `1..8` 时断言实际执行 `01..08`，输入 `8..12` 时断言实际执行 `08..12`，并验证使用注册表拓扑顺序。
- 停止边界：伪造一个包含多个安全单元的长步骤，在单元 N 提交后请求停止，断言单元 N 已保存、N+1 未启动、最终状态为 stopped。
- 检查点：断言每个成功单元提交后都能恢复，`next_unit_id`、范围、run ID、指纹和停止原因完整。
- 继续：恢复同一 checkpoint 时，断言成功单元不重复执行，只执行从 `next_unit_id` 开始的剩余单元。
- 幂等和竞态：覆盖停止与最后一个单元完成同时发生、重复点击停止、重复点击恢复、两个恢复请求竞争。
- 不匹配：修改项目/草稿/执行计划指纹后恢复必须被拒绝，并返回可操作错误。

### Tauri/API 与 Web 测试

- command 层对 `1`、`8`、`12` 的请求统一规范化，不依赖 Web 是否补零。
- stop command 更新的实时停止源能被正在运行的 worker 观察到；后台完成后不会用旧克隆状态覆盖停止结果。
- 应用重启/`load_pipeline_state` 后能展示 recoverable checkpoint；普通刷新不自动执行。
- Web 运行、停止、继续按钮状态随 `running`、`stopped`、`recoverable`、`completed`、`failed` 正确变化。
- 输入校验错误、不可恢复原因和恢复进度能显示在界面日志和状态区。

### 集成验收场景

1. 输入 `1` 到 `8`，点击运行，验证立即返回、后台按 `01..08` 执行并完成。
2. 在长步骤中点击停止，验证只在当前安全单元完成后停止，并产生可读 checkpoint。
3. 点击继续，验证从下一个单元执行，已完成单元没有重复副作用。
4. 停止后关闭并重新打开应用，验证可恢复状态可见；点击继续后运行完成。
5. 在停止请求与最后一步结束的竞态窗口重复测试，验证不会丢失停止请求或错误覆盖检查点。
6. 修改输入指纹后尝试恢复，验证被安全拒绝；选择重新运行步骤后能从新运行开始。
7. 回归 Step07 人工确认、普通单步运行、跳过人工门禁、失败/阻塞状态和现有产物展示。

实现完成后再执行项目规定的格式检查、Rust workspace 测试、Web 单元测试、Web 构建和 E2E/发布版 smoke；本次仅记录计划，未运行这些验证。

## 实施优先级

- **P0**：输入规范化、实时停止信号一致性、停止状态竞态修复、安全单元和 checkpoint 最小协议。
- **P1**：显式继续/恢复命令、重启/重连恢复、Web 输入和恢复交互、完整测试矩阵。
- **P2**：更细的步骤拆分、恢复审计展示、历史运行比较和更丰富的失败修复建议。

## 后续事项

- 本计划要求 Rust 对照 Python 的实际任务级恢复行为，但不应把 Python 当前的 `--resume`（iteration delta 专用）误用为流水线范围恢复 API。
- 对无法安全拆分的步骤，应明确显示“只能在步骤边界停止”，不能伪装成支持任意小阶段暂停。
- 真正实现后，需要补充一个跨层契约，确保 Web、Tauri command、流程 service、执行器和持久化 checkpoint 对同一 `run_id`、步骤 ID 和单元游标使用一致命名。
- 在用户仍要求“只写修复计划”的前提下，不得修改 Rust/Python/Web 代码；本文件只作为后续实现窗口的交接依据。
