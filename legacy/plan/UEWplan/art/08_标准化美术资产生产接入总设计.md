# 标准化美术资产生产接入总设计

## 目标

本方案用于替代当前 art 目录中偏“生成规格、后续再消费”的最小化口径。目标不是让流水线多产出几个 JSON，而是保证 AI 生成的图片经过标准资产管线后，能够在 Unity 中被导入、切片、打包、拼装、绑定、运行和验收。

最终定义：

- 一张图片只有同时具备 `asset_id`、真实文件、技术校验结果、语义校验结果、Unity 导入设置、切片结果、Prefab/场景挂载路径、程序绑定关系和验收记录，才算“可消费资产”。
- Step12 不能把不合格图片包装成成功输出；不合格资产必须进入返工队列，或使 Step12 进入 `completed_with_review` / `blocked`。
- Step13 不能只创建空 Canvas、空 GameObject 或占位引用；必须消费 Step12 的资产交付清单，生成 Unity 可加载资源和 UI Prefab。
- Step14 的验收必须覆盖上层设计需求，不只验证文件存在。

## 现有 art 计划的主要缺口

当前 `01` 到 `07` 文件已经覆盖了图像规格、切片、导入、Atlas、Prefab、绑定、验收这些主题，但存在以下结构性问题：

1. 多处把关键动作写成“只生成规格，不实际执行”。这会导致合同存在，但 Unity 中仍没有可用资产。
2. `image_spec_validation` 把像素检查设为可选、失败不阻断，这会继续允许概念图、气氛图、错误尺寸图进入后续步骤。
3. UI 切片只定义规则，不定义切片执行器、切片结果、失败返工和 Unity SpriteMetaData 写入方式。
4. Prefab 计划只生成层级描述，没有明确 Unity Editor 侧生成 Prefab、组件、Sprite 引用、事件绑定和保存资产的标准路径。
5. 程序绑定合同只记录规范，没有要求 Step13 自动注入字段和生成绑定报告。
6. Step14 验收仍偏向检查对象存在，未把“画面可见、可交互、状态变化、目标进度推进”作为完整游戏流程验收。
7. 缺少统一的资产生命周期状态机，导致 `generated`、`validated`、`processed`、`mounted`、`accepted` 之间没有闭环。

## 设计原则

### 强消费原则

每个上游合同都必须被下游实际读取并产生可验证结果。只写入 registry 或 schema 不算完成。

### 强阻断原则

以下情况必须阻断进入 Step13，或进入 `completed_with_review` 并被 Step13 门禁拦截：

- 必需 UI 资产不存在。
- 必需 UI 资产是概念图、参考图、moodboard、带水印图或不可切片图。
- 必需切片失败，且没有合规 fallback。
- 必需 Prefab 没有生成。
- 必需 UI 控件没有绑定 action / data binding / state observer。
- 资产无法映射到 Stage02/03/04/08/09 的来源合同。

### Unity 原生执行原则

Unity 资产落地应优先通过 Editor Script 调用 Unity API 完成，例如 `TextureImporter`、`SpriteMetaData`、`SpriteAtlas`、`PrefabUtility`、`SerializedObject`。除非已有可靠 writer，不应手写复杂 `.meta` 或 `.prefab` YAML。

### 通用游戏原则

设计必须适用于不同游戏类型。不能把工厂、资源面板、建造按钮作为硬编码模型。通用分类应使用：

- `screen`
- `panel`
- `control`
- `icon`
- `world_sprite`
- `character`
- `environment`
- `effect`
- `cursor`
- `placeholder_audio`

具体项目只通过合同中的 `usage`, `archetype`, `target_system`, `action_id`, `state_key` 表达。

### 可追溯原则

每个输出都必须保留 `source_refs`，至少能追踪到：

- Stage02 playable contracts。
- Stage03 program requirements。
- Stage04 asset contracts。
- Stage08 runtime tasks。
- Stage09 art production task contract。
- Step12 生成任务和原始图片。

## 标准资产生命周期

```text
required
  -> generated_raw
  -> intake_registered
  -> technically_validated
  -> semantically_validated
  -> processed
  -> import_ready
  -> atlas_ready
  -> prefab_ready
  -> binding_ready
  -> mounted_in_unity
  -> accepted
```

失败状态：

```text
rework_required
blocked_missing_source
blocked_invalid_image
blocked_slice_failed
blocked_import_failed
blocked_prefab_failed
blocked_binding_failed
blocked_acceptance_failed
```

状态推进必须由报告记录，不能只在日志中输出。

## 流水线分层

### Stage04：资产需求和消费规格

Stage04 不只是列出需要哪些资产，还必须输出可生产、可加工、可挂载的规格。

必需输出：

| artifact | 作用 | 下游 |
|---|---|---|
| `asset_registry.json` | 稳定资产身份、用途、优先级、目标路径 | Step05, Step09, Step10, Step12, Step13 |
| `asset_spec_contract.json` | 资产需求和验收口径 | Step09, Step12 |
| `image_consumable_spec.json` | 图像技术规格、透明度、尺寸、色彩、命名、禁止特征 | Step12 |
| `ui_slice_spec_contract.json` | UI 切片、九宫格、状态图、sprite sheet 规格 | Step12, Step13 |
| `unity_import_policy.json` | TextureImporter、压缩、平台、PPU、pivot、mipmap、Addressables 规则 | Step12, Step13 |
| `asset_usage_binding_seed.json` | 资产与 screen/control/action/state 的预绑定种子 | Step12, Step13 |
| `audio_placeholder_requirements.json` | 音频占位文件和后期音频需求，不要求真实音频 | Step12, Step13 |

### Step09：美术生产任务合同

Step09 必须把 Stage04 的规格转成可执行任务，而不是只列“生成图片”。

每个任务至少包含：

- `task_id`
- `asset_id`
- `asset_kind`
- `generation_prompt`
- `negative_prompt`
- `required_variants`
- `technical_spec_ref`
- `slice_spec_ref`
- `unity_import_policy_ref`
- `target_mount_ref`
- `acceptance_criteria`
- `rework_policy`

### Step12：美术生产和后处理

Step12 是图片从“生成结果”变成“Unity 可消费资产”的主流程，内部拆分为 8 个子阶段。

#### Step12-Art-01：Raw Intake

输入：

- Step09 `art_production_task_contract.json`
- AI 生成图片或占位资源
- Stage04 asset contracts

输出：

- `raw_generated_asset_manifest.json`

职责：

- 记录原始文件路径、生成参数、模型、时间、尺寸、hash。
- 区分 `raw_reference`、`raw_candidate`、`raw_placeholder`。
- 没有文件的必需资产必须标记为 blocking。

#### Step12-Art-02：Technical Validation

输出：

- `image_quality_report.json`

必检项：

- 文件存在和可读取。
- 格式白名单。
- 实际宽高。
- alpha 通道。
- 透明背景要求。
- 颜色模式。
- 文件大小。
- power-of-two 要求。
- 命名和路径规则。
- 禁止 marker，例如 `_concept`、`_reference`、`_draft`、`_moodboard`。

技术校验对必需资产是阻断项。环境缺少图像库时不能假成功，应标记 `environment_blocked`。

#### Step12-Art-03：Semantic Validation

输出：

- `art_semantic_review_report.json`

职责：

- 检查图片是否符合资产用途，例如按钮状态图不能是整张宣传图，图标不能包含复杂背景，HUD 元素不能带不可编辑文字。
- 检查风格一致性和 Stage07 style confirmation。
- 检查资产是否满足上层设计用途。

语义校验分两层：deterministic marker 检查必须实现并可阻断；复杂背景、水印、不可编辑文字等视觉内容检查需要 Vision AI 或人工审查。没有 Vision AI 时不能假装通过，应写入 `needs_human_review` / `vision_review_unavailable` 和返工队列。

#### Step12-Art-04：Image Normalization And Sprite Processing

输出：

- `processed_asset_manifest.json`
- `sprite_slice_result_manifest.json`

职责：

- 复制原始图到 Unity 源目录。
- 执行裁切、padding、trim、透明边缘清理、尺寸归一化。
- 对 UI 图片执行九宫格、状态图、sprite sheet 处理。
- 为每个切片生成稳定 `sprite_id`。
- 记录失败原因和返工建议。

如果没有本地图像处理依赖，必须在开发计划中引入依赖或 Unity Editor 处理器，不能把切片降级为“只生成规格”。

#### Step12-Art-05：Unity Import And Atlas Planning

输出：

- `unity_import_settings_manifest.json`
- `sprite_atlas_plan.json`
- `addressable_asset_plan.json`

职责：

- 为每个处理后资产生成完整 TextureImporter 设置。
- 定义 Sprite Mode、PPU、pivot、mesh type、mipmap、compression、platform override、alpha handling。
- 生成 Atlas 分组、最大尺寸、平台策略、Addressables key。
- 大图、背景图、动态加载图必须明确不进入 Atlas 的理由。

#### Step12-Art-06：Prefab Assembly Planning

输出：

- `ugui_prefab_contract.json`
- `ui_prefab_generation_request.json`

职责：

- 从 `ui_flow_contract` 和资产清单生成每个 screen 的 UGUI Prefab 结构。
- 定义 Canvas root、panel、control、layout、text、image、sprite 引用。
- 定义每个控件的 interaction state：normal、highlighted、pressed、disabled、selected。
- 定义每个控件的 action binding 和 data binding。
- 生成 Unity Editor 可以直接执行的 prefab generation request。

#### Step12-Art-07：Binding Preflight

输出：

- `asset_mount_manifest.json`
- `program_asset_binding_preflight.json`

职责：

- 检查 Prefab 节点、sprite_id、action_id、state_key 是否都有来源合同。
- 检查每个可交互 UI 控件都有程序消费方。
- 检查每个 runtime data binding 都有 UI 节点或明确无需显示的理由。

#### Step12-Art-08：Handoff And Rework Queue

输出：

- `art_handoff_manifest.json`
- `art_rework_queue.json`
- 更新 `art_production_report.json`

职责：

- 汇总可交付资产。
- 汇总阻断项和返工项。
- 为 Step13 生成唯一入口清单。
- 如果存在必需阻断项，Step12 不能 `succeeded`。

### Step13：Unity 资产物化和场景挂载

Step13 不能只读取合同后声明可挂载，必须把资产真正写入 Unity 项目。

必需动作：

1. 创建标准目录：
   - `Assets/AutoDesign/Art/Source`
   - `Assets/AutoDesign/Art/Processed`
   - `Assets/AutoDesign/Art/Atlas`
   - `Assets/AutoDesign/Prefabs/UI`
   - `Assets/AutoDesign/Runtime/Generated`
   - `Assets/AutoDesign/Audio/Placeholders`
   - `Assets/AutoDesign/Editor`
2. 复制或生成处理后资源文件。
3. 执行 Unity Editor Script：
   - 设置 TextureImporter。
   - 写入 Sprite 切片。
   - 创建 SpriteAtlas。
   - 创建 UGUI Prefab。
   - 给 Image/Button/Text/TMP/Slider 等组件赋值。
   - 注入 UIController/InputRouter/ObjectiveTracker 绑定。
4. 输出：
   - `unity_art_import_report.json`
   - `unity_prefab_generation_report.json`
   - `program_asset_binding_contract.json`
   - `unity_scene_mount_report.json`

Step13 必须对 Step12 的 `art_handoff_manifest.json` 做强门禁。没有 handoff 或 handoff 不 ready 时，Step13 blocked。

所有自动生成内容统一使用 `Assets/AutoDesign/` 作为根目录。既有 `Assets/Scenes/DemoScene.unity` 只作为场景路径；早期 `Assets/Art/...`、`Assets/Prefabs/...` 示例不再作为实现路径。首次写入 `Assets/AutoDesign/Editor` 下的 Editor Script 后，必须先触发 Unity 编译，再执行 `-executeMethod`。

### Step14：真实可玩验收

Step14 必须把美术验收纳入完整游戏流程验收。

验收层级：

| 层级 | 检查 | 失败后状态 |
|---|---|---|
| Level 1 静态合同 | artifact、source_refs、asset_id、binding_id 完整 | blocked |
| Level 2 Unity EditMode | importer、sprite、atlas、prefab、serialized field 存在 | failed |
| Level 3 PlayMode | 首屏 UI 可见、按钮可点击、状态变化、目标进度推进 | failed |
| Level 4 画面证据 | screenshot/pixel 检查，保证不是黑屏、空屏、全透明 UI | failed 或 environment_blocked |
| Level 5 上层需求追踪 | Stage02/03/04 的玩法、UI、输入、目标是否被满足 | failed |

输出：

- `art_acceptance_report.json`
- `playable_acceptance_report.json` 中合并 art 检查结果。

## 音频占位策略

当前不要求真实音频生成，但不能缺失音频需求链路。

要求：

- Stage04 输出 `audio_placeholder_requirements.json`。
- Step12 生成 `.audio_placeholder` 空文件和 `audio_placeholder_manifest_runtime.json`。
- Step13 把占位文件放入 Unity 标准目录并生成挂载占位记录。
- Step14 不要求播放真实音频，但要求音频需求、占位文件和后续生成提示存在。

真实音频 AI 接入时，只替换占位生产器，不改变挂载和验收合同。

## 完成定义

本方案完成后，不能再把“有图片文件”当作美术完成。完成标准是：

1. 每个 P0/P1 资产都有可追溯的生命周期状态。
2. 每个必需 UI 图片都已技术校验、切片或明确无需切片。
3. 每个 UI screen 都有 Prefab，并且 Prefab 中的 Image/Button/Text 等组件有真实引用。
4. 每个可交互控件都有 action binding。
5. 每个需要显示的 runtime state 都有 data binding。
6. Step13 物化 Unity 资产成功，并输出导入、Prefab、场景挂载报告。
7. Step14 能证明首屏不是空屏，UI 可见、可交互、状态能推进。
8. 任一关键环节失败时，流水线提供明确阻断报告和返工队列，而不是假成功。
