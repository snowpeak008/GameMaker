# 标准化美术资产管线开发计划

## 目标

本开发计划用于把 `plan/UEWplan/art` 中的标准化美术设计落地为可执行代码。目标不是最小修复，也不是只让流水线多产出几个 JSON，而是建立一条完整、标准、可追溯、可阻断、可验收的通用美术资产管线。

最终要解决的问题：

- AI 生成的图片不能再停留在概念图、气氛图、参考图状态。
- UI 图片必须经过规格校验、切片、Unity 导入配置、Prefab 拼装和程序绑定。
- Step13 必须能把 Step12 的资产真实写入 Unity 项目，而不是只生成合同。
- Step14 必须能证明 Unity 中有真实画面、真实 UI、真实交互和状态推进。
- 任一关键环节失败时，流水线必须产生明确阻断报告和返工队列，不能假成功。

## 设计依据

本计划以以下文件为准：

```text
plan/UEWplan/art/08_标准化美术资产生产接入总设计.md
plan/UEWplan/art/09_美术管线代码结构与合同标准.md
plan/UEWplan/art/10_标准化美术管线原子执行计划.md
```

`01` 到 `07` 的早期 art 计划只作为字段参考。若存在冲突，以 `08`、`09`、`10` 和本文档为准。

## 非目标

- 不为某个具体游戏类型写硬编码逻辑。
- 不用最小 MVP 路线跳过切片、Prefab、绑定或验收。
- 不把真实音频生成纳入本期范围；本期只生成音频占位文件和后续音频需求。
- 不继续把核心实现堆进 `core/engines/generation.py`。
- 不用 runtime `Find()` 作为正式绑定方案。

## 总体方案

新增独立美术管线模块：

```text
core/art_pipeline/
```

pipeline step 只负责读取输入、调用服务、写 artifact 和决定状态。实际业务逻辑放入 `core/art_pipeline/`。

核心流水线：

```text
Step04 资产消费规格
  -> Step09 美术生产任务合同
  -> Step12 生成图片 + 后处理 + handoff
  -> Step13 Unity 资产物化 + 场景挂载
  -> Step14 美术与玩法联合验收
```

## Unity 路径规范

本计划统一采用 `Assets/AutoDesign/` 作为自动生成内容根目录。所有由流水线生成、复制、切片、导入、打包、拼装、绑定的资源，都必须以该根目录为准生成 `unity_target_path`。

标准目录：

```text
Assets/AutoDesign/Art/Source
Assets/AutoDesign/Art/Processed
Assets/AutoDesign/Art/Atlas
Assets/AutoDesign/Prefabs/UI
Assets/AutoDesign/Runtime/Generated
Assets/AutoDesign/Audio/Placeholders
Assets/AutoDesign/Editor
```

兼容边界：

- `Assets/Scenes/DemoScene.unity` 可以继续作为场景文件路径；它不是美术资产根目录。
- 既有 `Assets/Scripts/` 可以继续作为手写或历史脚本路径；新增自动生成 runtime 脚本必须进入 `Assets/AutoDesign/Runtime/Generated`。
- 既有 `Assets/Editor/AutoDesignMaker/` 可作为历史 bootstrap 脚本兼容路径；新增 art pipeline Editor Script 默认写入 `Assets/AutoDesign/Editor`。
- 早期文档中的 `Assets/Art/...`、`Assets/Prefabs/...` 示例只作为旧示例，不作为实现路径。

Phase 01 必须把该目录规范写入 schema 和测试。Phase 03 生成 `unity_target_path`、Phase 11 写入 Unity 项目、Phase 12/14 验证路径时都必须使用同一根目录，不能在不同阶段重新推断路径。

资产生命周期：

```text
required
  -> generated_raw
  -> intake_registered
  -> technically_validated
  -> semantically_validated
  -> processed
  -> import_ready
  -> atlas_ready
  -> prefab_ready
  -> binding_ready
  -> mounted_in_unity
  -> accepted
```

失败状态：

```text
rework_required
blocked_missing_source
blocked_invalid_image
blocked_slice_failed
blocked_import_failed
blocked_prefab_failed
blocked_binding_failed
blocked_acceptance_failed
environment_blocked
```

目标：先建立合同边界，让后续代码有稳定输出目标。

修改范围：

```text

core/tests/unit/test_artifact_registry_playable_chain.py
```

实现内容：

- 为 Artifact 清单中的新增 JSON 创建 schema。
- `art_production_task_contract.schema.json` 已存在于 `knowledge/schemas/ai_design/`，Stage09 registry 也已注册；Phase 01 只能确认该 schema 和 registry 条目存在，不能新建同名 schema、移动路径或覆盖既有文件。
- 将 schema 注册到 `pipeline/artifact_layer/registry.json`。
- 定义并测试 Unity 自动生成内容根目录 `Assets/AutoDesign/`，所有 `unity_target_path`、`unity_prefab_path`、Atlas path 生成逻辑必须从同一目录策略读取。
- 处理 `dependency_graph.json` 时区分“确认已有边”和“新增边”：
  - 确认已有：Stage04 -> Stage09。
  - 确认已有：Stage12 -> Stage13。
  - 确认已有：Stage13 -> Stage14。
  - 新增：Stage09 -> Stage12，因为 Step12 直接消费 `art_production_task_contract.json`。
  - 新增：Stage04 -> Stage12，因为本计划要求 Step12 直接读取 `image_consumable_spec.json`、`ui_slice_spec_contract.json`、`unity_import_policy.json` 做强校验，不只通过 Step09 间接继承。

验收：

- registry 中引用的 schema 文件全部存在。
- `art_production_task_contract.schema.json` 使用既有文件，且既有 required 字段保持兼容。
- Step13 明确依赖 `stage_12/art_handoff_manifest.json`。
- Step14 明确依赖 Stage13 的 Unity import、Prefab、binding、scene mount 报告。
- 已有 dependency edge 不重复添加；新增 edge 有注释或测试证明消费关系。
- `unity_target_path`、`unity_prefab_path`、Atlas path 全部以 `Assets/AutoDesign/` 为自动生成根目录。

### Phase 06：语义审查与返工队列

目标：把“图片不能用”的视觉语义问题转成可执行返工任务。

修改范围：

```text
core/art_pipeline/services/semantic_validator.py
core/art_pipeline/services/rework_queue.py
```

输出：

- `art_semantic_review_report.json`
- `art_rework_queue.json`

语义校验分层：

- 第 1 层为必需 deterministic 检查：文件名、路径、metadata、asset kind、non_consumable_marker、任务用途和生成参数。该层不依赖 Vision AI；P0/P1 必需资产命中 `_concept`、`_reference`、`_moodboard`、`_draft`、`copyright`、`watermark` 等 marker 时必须 blocking。
- 第 2 层为视觉内容检查：复杂背景、水印、不可编辑文字、按钮状态错误、图标主体不清等需要 Vision AI 或人工审查。当前没有 Vision AI 接入时，不允许用不可靠启发式直接判定通过或失败；必须写入 `needs_human_review` 或 `vision_review_unavailable`，并进入 `art_rework_queue.json`。
- 若资产的 `semantic_policy.requires_visual_review=true`，Vision AI 不可用或人工审查未完成时，Step12 进入 `completed_with_review`，由 Step13 handoff 门禁决定是否继续。
- 若未要求视觉审查，视觉内容检查缺失只能作为 warning/review item，不能伪装成 passed。

验收：

- `_concept`、`_reference`、`_moodboard`、`_draft` 等必需资产阻断。
- UI 资产含复杂背景、水印、不可编辑文字等视觉问题时，必须通过 Vision AI 或人工审查确认；未接入 Vision AI 时进入 `needs_human_review`，不能自动判定通过。
- 返工项包含失败原因、修复方向、重新生成 prompt 建议。

### Phase 07：图像归档与 Sprite 切片元数据

目标：产生 Unity 可用的资产拷贝/命名结果和 sprite 切片元数据。实际 Sprite 切割、border/pivot 应用和 reimport 由 Phase 11 的 Unity Editor Script 执行，避免 Python 和 Unity 各自实现一套切片逻辑。

修改范围：

```text
core/art_pipeline/services/asset_normalizer.py
core/art_pipeline/services/sprite_slicer.py
```

输出：

- `processed_asset_manifest.json`
- `sprite_slice_result_manifest.json`

执行器职责边界：

- `sprite_slicer.py` 不执行实际像素切割、resize、crop、trim 或重新编码。
- Python 在 Phase 07 只负责复制/重命名源图片、登记 processed asset 路径、生成切片元数据 JSON。
- 切片元数据必须包含 `sprite_id`、`rect`、`border`、`pivot`、`pixels_per_unit`、`fallback_sprite_id` 和 `source_refs`。
- Pillow 只允许作为 Phase 05 图像探测的可选依赖，用于格式、尺寸、alpha 检查；Phase 07 不引入 Pillow 作为像素处理依赖。
- Phase 11 的 Unity Editor Script 消费 `sprite_slice_result_manifest.json`，通过 `TextureImporter` / `SpriteMetaData` / reimport 完成 Unity 内的实际 Sprite 切割。
- 如果某个资产需要真实像素级裁切、补边、重采样或透明边缘清理，而 Unity Importer 无法表达，Phase 07 必须写入 `visual_processing_required` / `needs_human_review` 或 rework queue，不能静默用 Python 做隐式处理。

实现要求：

- 复制/重命名并登记处理后资产路径，不做像素级切割或 resize。
- 支持 `single`、`nine_slice`、`button_state_set`、`grid_sheet`、`named_regions`。
- 为每个 sprite 生成稳定 `sprite_id`。
- 记录 pivot、rect、border、fallback 关系。

验收：

- UI button 至少有 normal、pressed、disabled；缺 highlighted 时必须有 fallback。
- 九宫格必须有四向 border。
- 切片失败的 P0/P1 资产阻断。
- Phase 07 不包含像素切割实现；测试应验证输出是 metadata manifest，并由 Phase 11 消费执行。

### Phase 08：Unity Import、Atlas、可选 Addressables 计划

目标：生成完整 Unity 导入配置和资源组织策略。

修改范围：

```text
core/art_pipeline/services/unity_import_planner.py
core/art_pipeline/services/sprite_atlas_planner.py
```

输出：

- `unity_import_settings_manifest.json`
- `sprite_atlas_plan.json`
- `addressable_asset_plan.json`，仅当 Unity 项目启用 Addressables 包或配置 `addressables_enabled=true` 时输出并参与门禁。

Addressables 规则：

- 默认资源引用策略是直接 prefab/sprite 引用，不强制使用 Addressables。
- Addressables 属于 P2 可选能力，不能成为所有项目的默认阻断条件。
- 未启用 Addressables 时，Step12 不生成 `addressable_asset_plan.json` 或生成 `status=not_applicable` 的非阻断报告。
- 启用 Addressables 时，必须生成稳定 key，并在 Step13/Step14 中验证 key 和 handle 生命周期。

验收：

- 每个 processed asset 有 TextureImporter 配置。
- 每个 sprite 有 PPU、pivot、sprite mode、compression、platform settings。
- 大图不进 Atlas 时必须记录理由。

Unity Editor Script 启动序列：

首次写入 `Assets/AutoDesign/Editor/AutoDesignAssetImporter.cs`、`AutoDesignPrefabBuilder.cs`、`AutoDesignSceneBinder.cs` 后，不能立刻假设 `-executeMethod` 可用。Step13 必须采用以下任一方式：

1. 两段式 batchmode：先执行 `Unity.exe -batchmode -projectPath <project> -quit -logFile compile.log` 触发脚本编译，再执行 `-executeMethod AutoDesignAssetImporter.Run` 等方法。
2. 预置 bootstrap：复用已有 `Assets/Editor/AutoDesignMaker/PlayableSceneBootstrapBuilder.cs` 模式，确保可执行入口在调用前已编译。
3. 若 Unity 编译失败或入口方法未发现，输出 `environment_blocked` 或 `failed`，不能把 Unity 资产物化标记为成功。

验收：

- 缺 `art_handoff_manifest.json` 时 Step13 blocked。
- `ready_for_step13=false` 时 Step13 blocked。
- 不允许只生成 JSON 后宣称 Unity 挂载完成。
- Editor Script 首次执行使用两段式 compile -> execute 序列，或使用已编译 bootstrap。
- Unity 不可用时输出 `environment_blocked`，保留静态报告。

### Phase 12：Step14 美术与玩法联合验收

目标：证明项目进入 Unity 后不是空屏，而是有完整可玩流程。

修改范围：

```text
core/art_pipeline/services/art_acceptance.py
pipeline/step_14_integration_validation/plugin.py
```

输出：

- `art_acceptance_report.json`
- 合并更新 `playable_acceptance_report.json`

验收层级：

| 层级 | 内容 | 失败状态 |
|---|---|---|
| Level 1 | artifact、source_refs、asset_id、binding_id 完整 | blocked |
| Level 2 | Importer、Sprite、Atlas、Prefab、SerializedField 正常 | failed |
| Level 3 | 首屏 UI 可见、按钮可点击、状态变化 | failed |
| Level 4 | 截图或像素检查不是黑屏、空屏、全透明 UI | failed / environment_blocked |
| Level 5 | Stage02/03/04 上层设计需求被覆盖 | failed / skipped_with_warning |

Level 4 最低验收阈值：

| 指标 | 标准 |
|---|---|
| 最小非透明像素比例 | 截图总像素中 `alpha > 0` 的像素比例 >= 5% |
| 首屏 Graphic 数量 | `activeSelf=true` 且 `enabled=true` 的 Unity UI `Graphic` 数量 >= 1 |
| 失败截图路径 | `outputs/artifacts/stage_14/screenshots/fail_<check_id>.png` |
| 截图格式 | PNG |
| 截图分辨率 | 优先 1920x1080；若运行环境无法固定分辨率，则记录实际分辨率 |
| 失败报告字段 | `check_id`、`screenshot_path`、`resolution`、`non_transparent_ratio`、`active_graphic_count`、`source_refs` |

Level 5 验证来源：

- Stage02 `playable_acceptance_contract.playmode_checks`。
- Stage02 `ui_flow_contract.playmode_checks`。
- Stage03 `program_requirements_contract.tasks[].acceptance` 或同等 acceptance 字段。
- Stage04 `asset_spec_contract.assets[].acceptance_check` 和 `asset_registry.assets[].purpose`。

Level 5 生成规则：

- 若上游存在验收来源，但 Step14 没有对应检查项或检查失败，则 Level 5 为 `failed`。
- 若上游验收来源文件缺失或字段为空，则 Level 5 为 `skipped_with_warning`，不能假成功，也不能因为没有来源而直接 failed。
- `skipped_with_warning` 必须写入 `art_acceptance_report.json` 和 `playable_acceptance_report.json`，提醒设计阶段合同不完整。

验收：

- 首屏没有 enabled Graphic 时 failed。
- Button 点击后 action 不触发时 failed。
- Data binding 无变化且设计要求变化时 failed。
- 上层设计要求存在但未覆盖时 failed；上层验收来源缺失时 skipped_with_warning。

## 状态门禁

### Step12 门禁

Step12 不允许 `succeeded` 的情况：

- P0/P1 required asset 缺文件。
- P0/P1 required asset 技术校验失败。
- P0/P1 UI 资产切片失败。
- Prefab 必需输入缺失。
- `art_handoff_manifest.ready_for_step13=false`。

### Step13 门禁

Step13 不允许继续的情况：

- 缺 `art_handoff_manifest.json`。
- `ready_for_step13=false`。
- mount item 缺 Unity target path。
- Unity 写入路径不可用。
- Prefab generation request 缺必需 screen。

### Step14 门禁

Step14 不允许通过的情况：

- Unity 中没有首屏 UI。
- Canvas、EventSystem、Camera、RuntimeBootstrap 不完整。
- Button 没有绑定 action。
- UI 数据绑定未能显示或更新。
- 上层设计中的可玩流程存在验收来源但未被覆盖。
