### 问题 1（P0）：`build_playable_contract_bundle()` 的 API 与结构化输入不兼容

**位置**：计划 07（D4 导出）第 5 步

**问题**：
计划 07 说"调用或扩展 `build_playable_contract_bundle()` 生成 candidates"。

但实际函数签名是：
```python
def build_playable_contract_bundle(parsed: dict[str, Any]) -> dict[str, Any]:
```
其中 `parsed` 内部必须包含 `parsed["selections"]`，即 `List[Selection]` 对象，每个 Selection 是从 Markdown 解析出来的结构体。

D4 拿到的是 `decisions.json`（结构化 node 决策），没有 `selections` 列表，也没有 `Selection` 对象。

**后果**：D4 在调用这个函数时，要么：
- 传入空 selections → 生成的 candidates 全是 fallback 默认值，等于没有用设计决策
- 试图构造假 Selection 对象 → 数据失真，traceability 断裂

**修复方向**：计划 07 或计划 02 中必须明确新增一个专门函数：
```python
def build_playable_contract_bundle_from_decisions(
    decisions: dict,
    profile: dict,
    archetype: str,
) -> dict[str, Any]:
```
该函数与现有函数并存，D4 使用新函数，旧函数仍被 Step02 的测试使用（保持向后兼容）。

### 问题 2（P0）：Plan 12（Step08）与 Plan 19（Step11）执行顺序倒置

**位置**：计划 00 执行序，第 13 行和第 14 行

**问题**：
执行序：
- 执行 13：计划 19（Step05-12 链路，含 Step11）
- 执行 14：计划 12（Step08 程序计划）

但是：
- **计划 19 的 Step11** 需要读取 Step08 的输出：`Step08 program plan`、`scene_assembly_task_requirements.json`
- **Step08 的输出格式**由计划 12 定义

实现 Step11（计划 19）时不知道 Step08 输出的 schema，实现者没有依据。同时计划 12 又依赖计划 19（`依赖 Step05到Step12中间链路强消费原子计划`），造成循环依赖。

**修复方向**：
- 把执行 14（计划 12）移到执行 13（计划 19）之前
- 或在计划 17（generation 策略）中定义 Step08 的输出合同 schema，计划 12 和计划 19 都引用它
- 计划 12 的"依赖"中去掉对计划 19 的依赖，计划 19 的 Step11 改为"依赖计划 12"

### 问题 3（P1）：`scene_bootstrap_contract.schema.json` 没有 `camera` 字段

**位置**：现有 schema 文件 + 计划 02（schema 扩展列表）

**问题**：
计划 03/07 都说"摄像机要求写入 `scene_bootstrap_contract.camera`"，计划 02 说要扩展 `scene_bootstrap_contract.schema.json`，但列举的扩展内容是：
> 将 `scene_bootstrap_contract.schema.json` 扩展为入口场景、根对象、摄像机、Canvas、EventSystem、输入根、目标追踪。

但**没有给出具体新字段名称**。

当前实际 schema 的 properties：`schema_version`, `engine`, `start_scene`, `runtime_roots`, `ui_roots`, `scene_acceptance`。

没有 `camera`、`input_root`、`objective_tracker`、`canvas_root`、`event_system` 等字段。

**后果**：实现者打开 schema 文件，不知道新 `camera` 字段叫什么、格式是什么，计划 03/07/08/12/13 所有引用 `scene_bootstrap_contract.camera` 的代码都无法实现。

**修复方向**：在计划 02 中明确补充字段定义，例如：
```json
"camera": {
  "type": "object",
  "required": ["projection", "position", "rotation"],
  "properties": {
    "projection": { "type": "string", "enum": ["Orthographic", "Perspective"] },
    "position": { "type": "array", "items": {"type": "number"}, "minItems": 3 },
    "rotation": { "type": "array", "items": {"type": "number"}, "minItems": 3 },
    "orthographic_size": { "type": "number" },
    "fov": { "type": "number" }
  }
},
"input_root": { "type": "string", "minLength": 1 },
"event_system": { "type": "string", "minLength": 1 },
"objective_tracker": { "type": "string", "minLength": 1 }
```

### 问题 4（P1）：`playable_acceptance_contract` 缺设计节点来源

**位置**：计划 03（节点元数据）、计划 06（D3 门禁）、计划 07（D4 导出）

**问题**：
`playable_acceptance_contract.schema.json` 中 `playmode_checks` 数组的每条记录需要：
- `check_id`
- `start_scene`
- `steps`（具体操作步骤）
- `expected_visible_text_or_object`
- `expected_state_change`
- `timeout_seconds`
- `blocking`

这些内容极其具体（"进入 Play 后先看到什么"、"点击哪里"、"观察什么变化"），必须来自设计决策。

但是：
- 计划 03 的 P0 节点清单中没有提到"验收合同来源节点"
- 计划 07 没有说明从哪个节点提取 `playmode_checks`
- D3 要检查"playable_acceptance_contract 是否可形成"，但没有来源则永远无法形成

**后果**：`playable_acceptance_contract` 只能依赖 `build_playable_contract_bundle()` 的默认值生成，全部是 fallback 占位，Step14 验收合同无实质内容。

**修复方向**：
1. 在计划 03 中，给 `data_test_design_decision` 节点（domain: `data_validation_design`）加上 `contract_targets: ["playable_acceptance_contract"]`
2. 在计划 07 中，说明从该节点的"体验测试"选项提取 `playmode_checks` 的规则
3. 或允许 acceptance contract 由 Step03（基于 `core_playable_contract` 的 action_verbs）自动生成基础版本，再允许设计节点补充定制

### 问题 5（P1）：Step07 人工确认机制在计划 19 中未被处理

**位置**：计划 19（Step07 美术风格确认）

**问题**：
现有 Step07（`step_07_art_style_generation`）代码中有特殊逻辑：
```python
confirmation = read_json(confirmation_path, {})
if not (isinstance(confirmation, dict) and confirmation.get("status") == "approved"):
    # 必须有人工确认才能继续
```

即：Step07 必须等待 `style_confirmation.json` 中 `"status": "approved"` 才能继续，这是一个**人工介入点**。

计划 19 把 Step07 描述为自动输出 `style_application_contract.json`，完全没有提到这个确认步骤。

**后果**：实现计划 19 的 Step07 时，如果直接跳过确认逻辑，会破坏现有的美术风格确认流程；如果保留确认逻辑，自动化端到端测试（计划 15）将无法通过 Step07，因为没有人工 `approved`。

**修复方向**：计划 19 中 Step07 部分需要明确：
- 确认逻辑是否保留（推荐保留，但端到端测试需要 mock `style_confirmation.json`）
- 自动确认场景（例如，test_mode=True 时跳过确认）
- 或定义"结构化合同中的美术方向决策可作为自动确认依据"的规则
