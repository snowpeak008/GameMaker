# 通用游戏完整设计合同与流水线强消费开发计划

## 1. 计划目的

本计划用于解决当前系统中最严重的一类质量问题：

> 设计阶段显示已经完成，开发流水线也继续执行，但最终 Unity 项目打开后没有可见 UI、没有可见场景、没有输入反馈、没有可玩流程。

本计划不是为某一个工厂建造游戏定制的修复方案，而是面向通用游戏项目的设计工作台与开发流水线升级方案。

目标是让任何游戏类型在进入开发流水线前，都必须拥有可被机器消费、可被验证、可被追溯的完整 playable contracts。

## 2. 修订结论

本计划以现有代码体系为基础，不新建第二套合同系统。

必须复用和扩展：

```text
core/ai_design/contract_gate.py
core/ai_design/types.py
core/ai_design/traceability.py
core/design/playable_contracts.py
knowledge/schemas/playable_contracts/
pipeline/artifact_layer/registry.json
```

禁止新增平行体系：

```text
core/design/contracts/
```

## 3. 当前问题重述

当前系统的问题不是单纯的 Unity 生成失败，而是设计交付链条不完整：

1. 设计工作台允许用户停留在抽象描述层。
2. D2/D3 更偏向检查设计知识库结构，而不是检查当前项目是否完成了真实设计决策。
3. D4 导出的设计交付物主要是 Markdown 与设计备注，缺少完整结构化 handoff。
4. Step00-14 仍有多处依赖 Markdown 推断。
5. Step05-09、Step08、Step10-12 中间链路如果不改，会重新把结构化合同链路打断。
6. Unity 阶段没有被强制要求生成并验证入口场景、Camera、Canvas/UIRoot、输入、目标和运行状态。

因此系统会出现假完成状态：

- 用户看到“设计完成”。
- 流水线看到“阶段成功”。
- Unity 项目里没有可玩的实际内容。

## 5. 设计原则

### 5.1 合同优先

自然语言文档可以存在，但不能作为流水线主要输入。开发流水线必须消费结构化 playable contracts。

### 5.2 不使用百分比作为主门禁

不能用“完成了 60% 节点”判断是否允许进入开发。通用游戏项目必须使用合同类型门禁。

例如：

- 缺 `ui_flow_contract`，不能进入完整 Unity 集成。
- 缺 `scene_bootstrap_contract`，不能进入 Step13。
- 缺输入动作或目标推进，不能通过 Step14。

### 5.3 通用核心 + 类型适配器

核心流水线不能绑定工厂建造、RPG、动作、解谜、卡牌等任何单一游戏类型。

系统分为两层：

- 通用 playable contracts。
- archetype 扩展规则。

类型特有内容只能通过 archetype adapter 或扩展合同进入，不能写死进核心 Step。

### 5.4 不靠 Markdown 解析驱动 P0 开发

`design.md` 用于人类阅读。P0 设计合同必须来自结构化 handoff、StageContext artifacts 和 playable contracts。

Markdown 只能作为兼容 fallback，并且必须输出 warning。

### 5.5 音频先定义需求，不强制生成真实音频

当前系统可以暂不接入音频生成 AI，但必须生成 `audio_requirements_contract`。

第一阶段音频策略：

- 记录 BGM/SFX/UI 音效需求。
- 使用 placeholder-first 方案。
- 默认占位路径沿用 `Assets/Audio/.audio_placeholder`。
- Step14 验证占位声明或 marker，不要求真实音频。

## 6. D4 Handoff 结构

D4 之后必须导出结构化 handoff，但正式开发消费仍以 Step02 冻结后的 Stage02 artifacts 为准。

现有 `package_manifest.json` 继续用于 devflow 包定位。新增 `structured/handoff_manifest.json` 只描述结构化 handoff 内容，并引用现有 package manifest，不替代它。

建议 D4 输出：

```text
output/devflow_Design_*/
  attachments/
    design.md
  structured/
    handoff_manifest.json
    decisions.json
    profile.json
    archetype_requirements.json
    traceability.json
    playable_contract_candidates/
      core_playable_contract.json
      demo_flow_contract.json
      runtime_data_contract.json
      ui_flow_contract.json
      scene_bootstrap_contract.json
      asset_mount_contract.json
      audio_requirements_contract.json
      playable_acceptance_contract.json
```

`attachments/design.md` 只用于人类阅读。`structured/` 才是 Step02 的输入来源。

traceability 规则：

- 合同内部 `source_refs` 是机器校验依据。
- 合同内部 `contract_refs` 是合同间依赖依据。
- `structured/traceability.json` 是字段级全量追溯索引。
- 三者并存但不能矛盾。

## 7. 设计状态模型

### 7.1 节点元数据

关键节点必须具备：

```json
{
  "priority": "P0",
  "requirement_level": "required",
  "contract_targets": ["ui_flow_contract", "scene_bootstrap_contract"],
  "required_for_archetypes": ["all"],
  "not_applicable_allowed": true,
  "not_applicable_requires_reason": true,
  "consumed_by_steps": ["Step13", "Step14"]
}
```

### 7.2 选项来源记录

必须新增 `optionProvenance`，否则无法判断 AI 建议是否被人工确认。

允许来源：

- `user_selected`
- `ai_inferred`
- `user_confirmed_ai`
- `migration_inferred`

D3 只允许 `user_selected` 和 `user_confirmed_ai` 计入完成。

### 7.3 Archetype

必须定义 archetype 枚举和必需合同映射。

第一批建议：

- `action`
- `puzzle`
- `strategy`
- `simulation`
- `rpg`
- `narrative`
- `management`
- `generic_playable`

## 8. D2/D3/D4 改造

### 8.1 D2：真实设计决策统计

D2 读取当前项目真实设计状态，输出：

- P0/P1/P2 完成情况。
- playable contract target 覆盖情况。
- AI inferred 未确认项。
- migration inferred 未确认项。
- 只有备注但无结构化决策的节点。

D2 不阻断，只报告。

### 8.2 D3：真实设计合同门禁

D3 必须阻断：

- 0 个真实决策。
- 缺 profile/archetype。
- 缺通用 P0 合同。
- 缺 `ui_flow_contract`。
- 缺 `scene_bootstrap_contract`。
- 缺输入动作。
- 缺目标推进。
- AI inferred 未确认。
- not_applicable 无 reason。

### 8.3 D4：结构化 handoff 导出

D4 必须导出：

- `decisions.json`
- `profile.json`
- `archetype_requirements.json`
- playable contract candidates。
- `traceability.json`

D4 生成 playable contract candidates 时，必须使用结构化入口：

```python
build_playable_contract_bundle_from_decisions(decisions, profile, archetype_requirements)
```

旧 `build_playable_contract_bundle(parsed)` 只保留为 Markdown 兼容入口。

D4 校验失败不能假 success。

## 9. 开发流水线强消费

### 9.1 generation.py 修改策略

必须先执行 `17_generation引擎结构化上下文重构策略.md`。

原则：

- 先新增 helper，不直接大拆 `generation.py`。
- P0 合同字段不再从 Markdown 解析。
- 所有正式输出对齐 artifact registry。
- 每个 Step 只改自己的输入适配层。
- 新增 stage artifacts 必须在 `pipeline/artifact_layer/registry.json` 的对应 stage `schema_refs` 中列出路径和 schema。

### 9.2 StructuredDesignContext

统一加载：

- D4 handoff。
- Stage02 playable contracts。
- 上游 stage artifacts。

API 不使用未定义的 `save_id`，而使用：

- `output_base_dir`
- `draft_session_id`
- StageContext/artifact 路径。

### 9.3 Step00-01

Step00/01 必须优先读取：

- `profile.json`
- `archetype_requirements.json`
- `decisions.json`

Markdown 只能补充摘要，不能覆盖结构化 profile。

### 9.4 Step02

Step02 冻结 D4 candidates 到：

```text
outputs/artifacts/stage_02/playable_contracts/
```

该路径必须与 `pipeline/artifact_layer/registry.json` 一致。

### 9.5 Step03

Step03 从 frozen playable contracts 生成程序需求：

- RuntimeBootstrap。
- GameState。
- InputRouter。
- UIController。
- ObjectiveTracker。
- SceneBootstrap。
- CameraRig。
- DataModel。
- TestHook。

### 9.6 Step04

Step04 从：

- `asset_mount_contract`
- `ui_flow_contract`
- `scene_bootstrap_contract`
- `audio_requirements_contract`

生成可消费资源需求和 Unity 挂载计划。

### 9.7 Step05-09

必须补齐 Step08 之前的审查和美术计划链路：

- Step05 程序审查。
- Step06 美术审查。
- Step07 风格确认。
- Step09 美术计划。

这些步骤不能重新退回 Markdown P0 解析。Step07 必须保留 `style_confirmation.json` 的 approved 确认门禁。

### 9.8 Step08

Step08 是程序计划阶段，不是实际 Unity 场景装配阶段。

它必须把 playable contracts 转化为 Step10/11/13 可执行任务：

- scene assembly task requirements。
- UI runtime task requirements。
- input runtime task requirements。
- objective runtime task requirements。

### 9.9 Step10-12

必须补齐 Step08 之后、Step13 之前的执行和生产链路：

- Step10 资产对齐。
- Step11 开发执行。
- Step12 美术生产。

Step11 必须依赖 Step08 已定义的输出 schema，不能在 Step08 之前实现。

### 9.10 Step13

Step13 是 Unity 场景装配阶段。

必须生成或验证：

- Entry Scene。
- RuntimeBootstrap。
- CameraRig。
- EventSystem。
- Canvas/UIRoot。
- 初始 HUD。
- InputRouter。
- ObjectiveTracker。
- GameState。
- 初始可见对象。
- 资源挂载。

### 9.11 Step14

Step14 使用分层验证：

- Level 1：静态结构验证。
- Level 2：Unity batchmode/EditMode。
- Level 3：PlayMode 行为验证。
- Level 4：可视化或像素验证。

Unity 环境不可用时输出 `environment_blocked`，不能假 success。

## 10. 测试策略

开发前必须先记录测试基线。

至少覆盖：

- `test_ai_design_contracts.py`
- `test_playable_contracts.py`
- D2/D3/D4 新测试。
- StructuredDesignContext 新测试。
- Step00-14 强消费测试。
- Step13 缺 UI/缺 Camera 阻断测试。
- Step14 分层验证测试。

## 11. 完成标准

本计划完成后，系统必须满足：

1. 空设计项目不能通过 D3。
2. 只有自然语言备注不能通过 D4。
3. 缺 `ui_flow_contract` 不能进入完整 Unity 集成。
4. 缺 `scene_bootstrap_contract` 不能进入 Step13。
5. 缺输入动作或目标推进不能通过 Step14。
6. D4 必须导出结构化 handoff。
7. Step00-14 必须按阶段消费结构化合同或 StageContext artifacts。
8. Unity Play 后必须有可见场景。
9. Unity Play 后必须有可见 UI。
10. 玩家输入必须产生状态变化。
11. 游戏目标必须能推进。
12. 所有关键生成物必须能追溯到设计合同字段。
