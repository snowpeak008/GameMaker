## 关键修复说明

### 1. handoff_manifest.json

计划 `07` 已明确：

- `handoff_manifest.json` 是新增文件。
- 不替代现有 `package_manifest.json`。
- 现有 `package_manifest.json` 继续用于 devflow 包定位。
- `handoff_manifest.json` 描述 structured handoff 内容，并引用 `../package_manifest.json`。

### 2. traceability 与 source_refs

计划 `07` 已明确：

- 合同内部 `source_refs` 是机器校验主要依据。
- 合同内部 `contract_refs` 是合同依赖依据。
- `structured/traceability.json` 是字段级全量索引。
- 三者并存但不能矛盾。
- 不一致时输出 `TRACEABILITY_MISMATCH`。

### 3. artifact registry 明细

计划 `12`、`19`、`20` 已列出需要新增或确认的 `schema_refs`：

- Step08: program plan、scene/UI/input/objective task requirements。
- Step05/06/07/09: review、style、art plan artifacts。
- Step10/11/12: alignment、dev execution、art production、audio placeholder artifacts。

计划使用现有 registry 风格，即 stage bundle 下的 `schema_refs`，而不是另建 artifact 索引格式。

### 4. ui_flow_contract 扩展策略

计划 `02` 已明确：

- 第一阶段新增 UI 字段为 optional。
- 不修改现有 required 列表。
- 旧 `build_playable_contract_bundle(parsed)` 不必为了新字段立即改动。
- 待新结构化入口稳定后再评估是否升级为 required。

### 5. D4 包查找

计划 `08` 已明确：

- 优先扩展现有 `_latest_concept_package()`。
- 或提取其 devflow 包扫描、manifest 读取、版本排序逻辑为公共函数。
- `StructuredDesignContext` 复用该逻辑，不重复实现扫描排序。

### 6. D3 可形成性算法

计划 `06` 已明确：

contract target 可形成，当且仅当 P0 贡献节点：

- `decision_state` 为 `selected` 或 `completed`。
- 至少一个相关选项来源为 `user_selected` 或 `user_confirmed_ai`。
- 或节点合法 not_applicable 且有 reason。

AI inferred、migration inferred、只有 designNote、未解决冲突都不能通过 D3。

第三轮审查提出的 6 个问题已经全部落到计划文件中。
