### 问题 1（P1）：`handoff_manifest.json` 格式从未定义

**位置**：计划 07 第 8 步，计划 08 第 2 步

**问题**：
计划 07 说"生成 `handoff_manifest.json`"，计划 08 说"读取 D4 `handoff_manifest.json`"。但两个计划都没有定义这个文件的字段结构。

对照代码库：现有 `_latest_concept_package()` 通过读取 `package_manifest.json` 的 `stage`、`source_ids`、`package_type` 字段来定位 D4 包。**新的 `handoff_manifest.json` 与旧的 `package_manifest.json` 是同一个文件还是不同文件？** 计划没有说明。

如果是同一个文件（扩展现有的），需要说明新增哪些字段。如果是新文件，需要定义完整格式，并解释为何不扩展现有文件。

**后果**：
- 计划 08 实现者不知道 `handoff_manifest.json` 有哪些字段，无法实现加载逻辑
- `StructuredDesignContext.from_output_base()` 找不到 D4 包，或找到错误的包

**修复方向**：在计划 07 中补充最小格式定义，并明确与现有 `package_manifest.json` 的关系。建议示例：
```json
{
  "schema_version": "1.0",
  "handoff_type": "structured_design_handoff",
  "generated_at": "ISO-8601",
  "project_id": "string",
  "structured_dir": "structured/",
  "contracts": [
    { "contract_id": "core_playable_contract", "path": "structured/playable_contract_candidates/core_playable_contract.json", "schema_version": "1.0" }
  ],
  "decisions_path": "structured/decisions.json",
  "profile_path": "structured/profile.json",
  "archetype_path": "structured/archetype_requirements.json",
  "traceability_path": "structured/traceability.json"
}
```

### 问题 2（P1）：`traceability.json`（独立文件）与各合同内嵌 `source_refs` 关系未定义

**位置**：计划 07（生成 `traceability.json`）vs 计划 09（frozen contracts 包含 source_refs）

**问题**：
计划 07 说 D4 导出独立文件 `traceability.json`，记录"合同字段来自哪个节点"。  
计划 09 说"frozen contracts 包含 traceability/source_refs"（内嵌在每个合同内部）。  
现有 `validate_contract()` 检查合同内部的 `source_refs` 字段。

这是三种不同的 traceability 表达方式，计划没有说明它们的关系：

| 方式 | 位置 | 当前计划状态 |
|------|------|------------|
| 独立 `traceability.json` | `structured/traceability.json` | 计划 07 要求导出 |
| 合同内嵌 `source_refs` | 每个合同的 `source_refs` 字段 | 计划 09 要求；现有 validator 检查 |
| 合同内嵌 `contract_refs` | 每个合同的 `contract_refs` 字段 | 现有 validator 检查 |

**后果**：实现者会在以下问题上犯错：
- 是否需要维护两套 traceability（合同内嵌 + 独立文件）？
- 当两套不一致时哪个为准？
- Step02 冻结时是否要同时复制 `source_refs` 进每个合同？

**修复方向**：在计划 07 中明确一句话的规则，例如：
> `traceability.json` 是合同级别字段到设计节点的全量索引，供人类可读和调试。各合同内部 `source_refs` 字段是该合同范围内的来源引用，供 `validate_contract()` 机器校验。两者并存，`source_refs` 是合同自验证的主要依据，`traceability.json` 是全量可追溯记录。

### 问题 4（P2）：`ui_flow_contract` schema 扩展未说明新字段是 required 还是 optional

**位置**：计划 02 第 6 步

**问题**：
计划 02 说"将 `ui_flow_contract.schema.json` 扩展为屏幕图、HUD、数据绑定、输入入口和空状态"。

现有 schema 已有 required：`ui_framework`、`screens`、`data_bindings`、`playmode_checks`。  
新要添加的"输入入口"（类似 `input_entries`）是 **required** 还是 **optional**？

对照现有测试 `test_playable_contracts.py`，旧函数 `build_playable_contract_bundle(parsed)` 输出的 `ui_flow_contract` 中：
- 没有 `input_entries` 字段
- 有 `screens[0]["screen_id"] == "game_hud"`

如果新字段成为 required，旧函数生成的合同无法通过 schema 校验，`test_playable_contracts.py` 测试将失败（尽管计划 02 的完成标准第 3 条提到"仍通过或按新 schema 明确更新"）。

**后果**：实现者对"是否需要同时修改旧函数"判断不一致，导致旧测试随机通过或失败。

**修复方向**：在计划 02 第 6 步补充一句：
> 新扩展字段（如 `input_entries`、`empty_state_handling`）在第一阶段为 `optional`，不修改 `required` 列表。旧 `build_playable_contract_bundle()` 无需修改，旧测试不受影响。待新函数覆盖完整后，再评估是否升级为 required。

**位置**：计划 08 第 1 步"实现 handoff 查找逻辑"

### 问题 6（P2）：D3 "contract 可形成性"检查算法在计划 06 中未明确

**位置**：计划 06 第 4 步

**问题**：
计划 06 说"检查 contract target 可形成性"，但没有定义判断算法：

- 是检查贡献节点的 `decision_state` 是否为 `selected`/`completed`？
- 是检查 `optionProvenance` 是否有 `user_selected` 或 `user_confirmed_ai`？
- 是检查 `checklistOptions` 中选中数量是否超过某个阈值？
- 还是直接调用 `build_playable_contract_bundle_from_decisions()` 并检查 fallback 比例？

这个判断决定了一个 P0 节点"已完成"但全部选项是 `ai_inferred` 时，是否能让 contract 被视为"可形成"。

**后果**：不同实现者对"可形成性"的判断可能不同，导致 D3 门禁标准不一致，某些情况下 AI 推断内容错误地通过 D3。

**修复方向**：在计划 06 中补充一段明确算法：
> contract 被视为"可形成"当且仅当：该合同的所有 P0 贡献节点，满足以下条件之一：
> (a) `decision_state ∈ {selected, completed}` 且至少有一个 `checklistOptions` 的选项 `optionProvenance.source ∈ {user_selected, user_confirmed_ai}`；
> (b) 节点被标记为 `not_applicable` 且有 reason；
> 否则视为"不可形成"，D3 返回 blocked。
