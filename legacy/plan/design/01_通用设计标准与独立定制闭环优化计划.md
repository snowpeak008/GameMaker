# 通用设计标准与独立定制闭环优化计划

> 日期：2026-07-04  
> 目标路径：`plan/design/`  
> 适用范围：设计工作台、D1-D4 设计交接、开发流水线 Step00-10，并向 Step11-14 提供可消费的上游合约。  

---

## 1. 问题定义

本轮并行测试中，“植物大战僵尸”和“请出示证件”两个项目均完成 Step00-10，且制品门禁显示 success。但检查实际产物后发现：

1. Step08 程序开发计划在两个项目中高度相似，核心任务基本都是 `RuntimeBootstrap`、`GameState`、`InputRouter`、`UIController`、`SceneBootstrap` 等通用运行时任务。
2. Step09 美术制作计划生成了大量通用资产，如 `asset_ui_placeholder`、`asset_fallback_visual`、`ui_prefab_game_hud`，缺少项目真实资产拆解。
3. Step10 资源对齐报告显示 `gaps=0`，但对齐的是通用 placeholder，并不是项目真实玩法、美术、UI、场景需求。
4. 部分上游合约存在空字段，例如 Step02 的 `systems` 出现空对象，Step04 的资产字段出现空值，说明当前门禁更偏结构验证，不足以判断语义完整。
5. 计划产物中仍出现历史模板说明残留，说明模板来源没有被标准化隔离，也没有被项目定制层完全吸收。

因此，当前问题不是单个游戏模板质量问题，而是设计流水线缺少一个强制机制：让“通用标准结构”必须被“项目独立语义”填满，并且后续程序计划、美术计划、资源对齐必须消费这些语义。

---

## 2. 目标

本计划的目标是建立一套通用设计标准，使系统既能支持任意 2D 游戏类型，又能保证每个项目生成独立、可执行、可消费的项目内容。

### 2.1 核心目标

1. 每个项目必须生成独立的 `Project DNA`，包含核心玩法、实体、动作、资源、目标、场景、UI、输入、美术、音频占位、验收场景。
2. 通用模板只能作为起点，不能直接成为下游开发计划。
3. Step08 程序开发计划必须从项目专属系统和需求生成，不能只生成通用运行时任务。
4. Step09 美术制作计划必须从项目专属资产分类生成，不能只生成 placeholder。
5. Step10 资源对齐必须验证项目核心内容是否被程序和美术共同消费，而不是只验证路径和文件存在。
6. 如果 AI 补全参与设计，AI 输出必须进入可追踪合约，并经过结构校验、语义校验和人工确认状态标记。

### 2.2 非目标

1. 本计划不是为了专门修复植物大战僵尸或请出示证件两个项目。
2. 本计划不要求复制任何商业游戏的完整内容或 IP 表现。
3. 本计划不以最小 MVP 为目标，不允许只用一个通用 Demo 框架绕过设计缺口。
4. 本计划不在当前阶段实现真实音频生成，只生成音频占位、音频事件和后续接入需求。

## 3. 总体设计原则

### 3.1 三层设计标准

每个项目的设计内容分为三层：

| 层级 | 职责 | 示例 |
|---|---|---|
| 通用标准层 | 所有游戏都必须具备的结构 | 核心循环、玩家动作、状态数据、目标、UI、输入、场景、验收 |
| 类型范式层 | 某一类游戏的专业结构 | 塔防的路径/波次/建造/资源；证件审查的规则/文件/判定/惩罚 |
| 项目定制层 | 当前项目独有的实际内容 | 具体单位、资源、关卡结构、UI 面板、检查流程、失败条件 |

任何下游产物都不能只停留在通用标准层。Step03-10 至少必须消费类型范式层和项目定制层。

### 3.2 项目语义优先

同一套代码结构可以通用，但设计内容不能通用。  
程序任务标题、任务验收、美术任务、资产路径、UI 需求、输入动作、场景装配任务都必须包含项目语义。

例如：

| 不合格 | 合格 |
|---|---|
| Implement GameState | Implement lane defense state: lanes, sun resource, plant slots, wave timer |
| Create fallback visual | Create passport inspection desk prefab, passport document sprite, rulebook UI |
| Align assets | Bind plant unit sprites, zombie sprites, sun icon, lane grid, HUD counters |

### 3.3 占位符必须有边界

placeholder 可以存在，但只能用于以下场景：

1. 音频真实生成暂未接入时的静音占位。
2. Unity 首次可见画面的临时 fallback。
3. 缺少真实图片模型时的人工复核队列。

placeholder 不能替代项目核心资产，也不能让 Step09/10 误判为完整。

### 3.4 结构通过不等于内容通过

所有关键步骤都需要双重门禁：

1. 结构门禁：JSON schema、路径、依赖、必填字段。
2. 语义门禁：核心实体是否被消费，项目动作是否进入任务，项目资产是否进入生产计划，验收是否覆盖真实玩法。

## 4. 新增核心合约

```json
  "project_id": "current_save_or_project_id",
  "project_name": "项目名",
  "template_origin": {
    "template_id": "可选",
    "reference_name": "可选",
    "legal_status": "reference_only"
  },
  "archetype": {
    "primary": "tower_defense | document_inspection | platformer | ...",
    "secondary": []
  },
  "core_loop": {
    "steps": [],
    "success_condition": "",
    "failure_condition": ""
  },
  "core_entities": [],
  "player_actions": [],
  "resources": [],
  "objectives": [],
  "scene_model": {},
  "ui_surfaces": [],
  "input_model": [],
  "art_taxonomy": [],
  "audio_event_placeholders": [],

```

用于记录项目语义是否被各步骤消费。

最低字段：

```json

  "project_id": "current_project",
  "source_contract": "stage_02/project_dna_contract.json",
  "coverage_items": [
```

用于让每一步可量化评分，不再只显示 success。

## 5. 步骤改造方案

### 5.1 设计工作台 / D1-D4

目标：模板不再直接作为开发依据，而是被转化为当前项目的独立设计语义。

改造内容：

1. 模板选择后生成 `template_normalization_contract.json`。
2. AI 补全只允许补足缺失设计项，不允许覆盖用户显式选择。
3. 模板中的参考游戏名、历史说明、反推说明不得进入 Step08/09 的任务标题和资产名。
4. D4 导出时必须携带：
   - 项目名
   - 类型范式
   - 核心循环
   - 核心实体
   - 玩家动作
   - 资源与数值
   - 场景结构
   - UI 结构
   - 资产需求
   - 验收场景

新增门禁：

| 代码 | 含义 |
|---|---|
| `PROJECT_DNA_MISSING` | 未生成项目语义根 |
| `TEMPLATE_LEAKAGE` | 下游任务仍直接暴露历史模板说明 |
| `UNCONFIRMED_AI_COMPLETION` | AI 补全内容未标记来源和确认状态 |

### 5.2 Step00 创意收集

目标：不再允许项目身份模糊。

改造内容：

1. `concept_profile.json` 必须输出非空 `genre`、`genre_key`、`archetype`。
2. 如果只能识别为 `generic`，必须生成 warning；如果项目已有明确模板但仍为 `generic`，应 blocking。
3. 输出 `project_identity_contract.json`，记录项目指纹。
4. 输出初版 `project_dna_contract.json`，至少包含项目名、类型、核心循环、已知实体、已知动作。

评分标准：

| 指标 | 阈值 |
|---|---|
| 项目身份完整度 | >= 0.9 |
| 类型识别可信度 | >= 0.8 |
| 核心循环可解析度 | >= 0.8 |

### 5.3 Step01 玩法框架

目标：把抽象玩法转成类型范式和项目定制内容。

改造内容：

1. 引入 `archetype_requirements.json`，不同类型有不同最低要求。
2. 塔防类必须有路径/车道/敌人推进/防御部署/资源产出/波次。
3. 证件审查类必须有文件/规则/检查动作/判定/惩罚/日结。
4. 其他类型按类型范式扩展，不使用固定清单硬套所有项目。
5. 更新 `project_dna_contract.json` 中的 `core_entities`、`player_actions`、`resources`、`objectives`。

新增门禁：

| 代码 | 含义 |
|---|---|
| `ARCHETYPE_REQUIREMENTS_UNMET` | 类型最低结构未满足 |
| `CORE_LOOP_TOO_GENERIC` | 核心循环只有通用描述 |
| `PLAYER_ACTIONS_MISSING` | 没有可执行玩家动作 |

### 5.4 Step02 设计冻结

目标：冻结的是可开发设计，而不是空字段结构。

改造内容：

1. 禁止 `systems`、`entities`、`assets` 出现关键字段全空对象。
2. 冻结 `project_dna_contract.json`，后续步骤只能消费，不允许静默改写。
3. 输出 `playable_scenario_contract.json`，定义第一可玩流程。
4. `playable_acceptance_contract.json` 必须引用项目真实语义。

新增门禁：

| 代码 | 含义 |
|---|---|
| `NULL_CONTRACT_FIELD` | 冻结合约出现关键空字段 |
| `PLAYABLE_SCENARIO_MISSING` | 没有第一可玩场景 |
| `CORE_ENTITY_UNFROZEN` | 核心实体没有进入冻结合约 |

### 5.5 Step03 程序需求

目标：生成项目专属程序需求，而不是只生成运行时框架需求。

改造内容：

1. 从 `project_dna_contract.json` 生成 `program_capability_contract.json`。
2. 每个核心实体至少绑定一个程序能力。
3. 每个玩家动作至少绑定输入、状态变化和验收。
4. 每个资源至少绑定数据模型和 UI 展示要求。
5. 每个目标至少绑定完成条件和失败条件。

示例：

| 项目 | 必须出现的程序能力 |
|---|---|
| 塔防 | lane grid、unit placement、resource economy、enemy wave、collision/reach-goal |
| 证件审查 | document model、rulebook、inspection action、approval/rejection、penalty/day summary |

新增门禁：

| 代码 | 含义 |
|---|---|
| `PROGRAM_CAPABILITY_NOT_BOUND` | 核心语义未绑定程序能力 |
| `ACTION_HAS_NO_STATE_CHANGE` | 玩家动作没有状态变化 |
| `RESOURCE_HAS_NO_DATA_MODEL` | 资源没有数据模型 |

### 5.6 Step04 美术需求

目标：生成项目可消费资产分类，而不是通用 placeholder。

改造内容：

1. 输出 `art_taxonomy_contract.json`。
2. 资产分类至少覆盖：
   - 角色/单位
   - 场景/空间
   - UI/HUD
   - 图标/资源
   - 反馈/VFX
   - 状态变化
   - 音频占位事件
3. 每个核心实体必须有资产策略：真实图片、程序图形、占位、后续人工制作。
4. UI 图片必须输出 slice 或 prefab 需求。
5. 音频只生成空文件需求和事件映射，不声明真实音频已完成。

新增门禁：

| 代码 | 含义 |
|---|---|
| `ASSET_TAXONOMY_UNDERCOVERED` | 资产分类覆盖不足 |
| `CORE_ENTITY_WITHOUT_ASSET_STRATEGY` | 核心实体没有资产策略 |
| `PLACEHOLDER_AS_FINAL` | 占位符被标记为最终资产 |

### 5.7 Step05 / Step06 AI 评审

目标：评审必须检查语义完整度。

改造内容：

1. Step05 检查程序需求是否消费 Project DNA。
2. Step06 检查美术需求是否消费 Project DNA。
3. 新增 `customization_score_report.json`。
4. 当 `generic_template_ratio` 过高时 blocking。
5. 当 project-specific terms 在 Step03/04 中覆盖不足时 blocking。

建议阈值：

| 指标 | Blocking 阈值 |
|---|---|
| `required_semantic_coverage` | < 0.85 |
| `generic_template_ratio` | > 0.45 |
| `placeholder_ratio` | > 0.35，音频占位除外 |

### 5.8 Step07 风格确认

目标：风格必须服务项目类型和可读性。

改造内容：

1. 风格选项必须包含适配理由。
2. 风格确认必须输出：
   - 视角适配
   - UI 可读性
   - 资产生产难度
   - 核心实体表现能力
3. 如果风格与玩法冲突，应 blocking 或要求人工确认。

示例：

| 风格问题 | 处理 |
|---|---|
| 塔防选择 cinematic realism 导致单位可读性差 | warning 或 blocking |
| 证件审查选择高饱和卡通导致文本审查氛围冲突 | warning |

### 5.9 Step08 程序开发计划

目标：把程序需求变成项目专属开发任务。

改造内容：

1. `program_plan_contract.json` 的任务必须分为：
   - runtime foundation
   - project gameplay systems
   - project data models
   - UI flow
   - input/actions
   - scene/bootstrap
   - acceptance tests
2. 通用任务可以存在，但不能超过一定比例。
3. 每个任务必须包含 `project_semantic_refs`。
4. 任务标题必须体现项目语义，不能全部是通用类名。
5. 输出 `semantic_coverage_matrix.json`，说明 Step08 消费了哪些 Project DNA 项。

新增门禁：

| 代码 | 含义 |
|---|---|
| `GENERIC_PLAN_DOMINANCE` | 通用任务占比过高 |
| `PROGRAM_TASK_WITHOUT_PROJECT_REF` | 程序任务没有项目语义引用 |
| `CORE_MECHANIC_NOT_PLANNED` | 核心机制没有开发任务 |

### 5.10 Step09 美术制作计划

目标：美术任务必须是项目资产任务。

改造内容：

1. `art_production_task_contract.json` 必须从 `art_taxonomy_contract.json` 生成。
2. 每个核心实体、UI 面板、关键反馈至少有一个资产任务或明确的非图片实现策略。
3. `generation_prompt` 必须包含：
   - 资产用途
   - 项目语境
   - 视觉状态
   - 尺寸或使用位置
   - Unity target path
   - slice/prefab/import 策略
4. placeholder 任务必须单独分类，不能算入核心资产覆盖率。
5. 输出 `art_semantic_coverage_matrix.json`。

新增门禁：

| 代码 | 含义 |
|---|---|
| `ART_TASK_TOO_GENERIC` | 美术任务只描述通用资产 |
| `CORE_ASSET_NOT_PRODUCED` | 核心资产没有生产任务 |
| `PROMPT_MISSING_USAGE_CONTEXT` | 生成提示词缺少使用场景 |

### 5.11 Step10 资源对齐

目标：对齐项目核心需求，而不是对齐文件名。

改造内容：

1. 对齐矩阵必须同时检查：
   - Project DNA 项
   - 程序任务
   - 美术任务
   - UI prefab 请求
   - Scene assembly 需求
   - PlayMode 验收
2. `gaps=0` 的前提是项目核心语义全部覆盖。
3. 如果只有 fallback 或 placeholder 覆盖，必须标记为 `covered_by_placeholder`，不能算 fully covered。

新增门禁：

| 代码 | 含义 |
|---|---|
| `SEMANTIC_ALIGNMENT_GAP` | 项目语义未被程序/美术共同覆盖 |
| `PLACEHOLDER_ONLY_ALIGNMENT` | 只由占位符覆盖核心需求 |
| `UI_PREFAB_REQUEST_MISSING` | UI 资产没有 prefab 请求 |

## 6. 对 Step11-14 的影响

虽然本计划重点在 Step00-10，但必须保证后续可执行。

| 步骤 | 影响 |
|---|---|
| Step11 程序执行 | 根据项目专属程序任务生成代码，不再只生成通用 Demo 代码 |
| Step12 美术生产 | 根据项目专属资产任务生成图片、占位、切片和 handoff |
| Step13 场景组装 | 读取项目语义和资源绑定，组装真实 UI、场景、输入、可见内容 |
| Step14 集成验证 | 验证上层设计需求是否被满足，而不是只验证黑屏/报错 |

## 7. 评分体系

每个步骤除 success/failed 外，新增 10 分制质量评分。

| 分数 | 含义 |
|---|---|
| 9-10 | 结构完整、项目语义充分、可直接消费 |
| 7-8 | 结构完整，少量人工确认或轻微缺口 |
| 5-6 | 可以继续跑，但内容偏模板化或覆盖不足 |
| 3-4 | 关键项目语义缺失，下游大概率生成通用 Demo |
| 0-2 | 合约无效、缺失关键产物或无法消费 |

每步最低建议：

| 步骤 | 最低分 |
|---|---:|
| Step00 | 8 |
| Step01 | 8 |
| Step02 | 8.5 |
| Step03 | 8 |
| Step04 | 8 |
| Step05 | 8 |
| Step06 | 8 |
| Step07 | 7.5 |
| Step08 | 8.5 |
| Step09 | 8.5 |
| Step10 | 8.5 |

低于最低分时，可以允许人工确认继续，但必须在下游产物中保留 `quality_debt`，不能静默当作完整设计。

## 8. 并行项目隔离要求

为了支持 10 个甚至更多项目并行运行，设计语义和评分文件必须带有明确归属。

要求：

1. 所有新增合约必须包含 `save_id`、`draft_id`、`project_id` 或等价运行上下文。
2. AI prompt 必须注入当前项目 source root，禁止读取“最近草稿”作为默认依据。
3. 模板缓存必须按模板文件签名和项目选择签名隔离。
4. 语义覆盖矩阵只能读取当前 save/workspace 的制品。
5. Step08/09/10 的验收必须检查 source refs 是否属于当前项目。

新增门禁：

| 代码 | 含义 |
|---|---|
| `SOURCE_REF_CROSSES_SAVE` | 产物引用了其他存档或草稿 |
| `PROJECT_SIGNATURE_MISMATCH` | 下游产物项目签名与当前项目不一致 |
| `TEMPLATE_CACHE_STALE` | 模板缓存签名与当前输入不一致 |

## 9. 实施分解

### Phase 00：基线与诊断

## 10. 验收标准

### 10.1 植物大战僵尸类项目验收样例

Step08 中应出现类似任务：

- 车道网格/格子占位系统
- 阳光资源生成与消耗
- 植物放置与冷却
- 敌人波次推进
- 植物攻击与敌人受击
- HUD 显示阳光、波次、目标状态

Step09 中应出现类似资产：

- 草坪/车道背景
- 植物单位 sprite
- 敌人单位 sprite
- 阳光图标
- 种植卡片 UI
- 波次提示 UI
- 攻击/命中反馈

### 10.2 请出示证件类项目验收样例

Step08 中应出现类似任务：

- 证件数据模型
- 规则书与每日规则变更
- 文件字段核验动作
- 批准/拒绝判定
- 错误惩罚
- 日结与家庭经济
- 检查台 UI/文件拖拽或选择操作

Step09 中应出现类似资产：

- 检查台场景
- 护照/证件图片
- 印章或批准拒绝按钮
- 规则书 UI
- 入境者头像或剪影
- 日结面板
- 警告/错误反馈图标

### 10.3 通用验收

任意项目都必须满足：

1. Step00-10 不得只生成通用 Demo 任务。
2. Step08 至少 50% 任务为项目专属任务。
3. Step09 核心资产覆盖率 >= 85%。
4. Step10 required semantic coverage >= 85%。
5. placeholder 不能覆盖核心玩法必需资产。
6. `gaps=0` 必须代表语义完整，不只是路径完整。

## 11. 风险与处理

| 风险 | 处理 |
|---|---|
| 类型范式过多，难以一次完成 | 先实现通用 archetype schema，再逐步补充类型库 |
| AI 补全生成虚假内容 | 所有 AI 补全必须标记 source、confidence、confirmation |
| 门禁过严导致早期项目无法继续 | 允许人工确认继续，但保留 quality_debt，不允许伪装为完整 |
| 美术资产数量暴涨 | 引入优先级：P0 可玩必需、P1 表现增强、P2 后续扩展 |
| 参考游戏模板存在版权风险 | 模板作为结构参考，不输出商业 IP 名称和直接可侵权内容 |

---

## 12. 最终预期

完成本计划后，系统应具备以下能力：

1. 同时并行 10 个项目时，每个项目有独立 Project DNA。
2. 同一套标准流程可以支持不同 2D 游戏类型。
3. 每个项目的程序计划、美术计划、资源对齐都体现项目独立定制内容。
4. Step08/09 不再退化为通用 Runtime + placeholder 计划。
5. Step10 的 `gaps=0` 具有真实意义，代表项目核心语义被覆盖。
6. 后续 Step11-14 能生成更接近真实玩法流程的 Unity Demo，而不是只有空场景、通用 HUD 或 fallback visual。
