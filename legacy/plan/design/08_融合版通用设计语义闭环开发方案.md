## 1. 方案定位

这是一份融合开发方案，目标不是再新增一组零散优化点，而是把现有方案整合为一条稳定、可执行、可验证的设计语义闭环。

核心目标：

1. 通用标准：任意 2D 游戏项目都使用同一套设计合约、门禁、评分和下游消费协议。
2. 独立定制：不同项目必须生成不同的核心实体、动作、资源、UI、资产、程序任务和验收场景。
3. 强制下沉：设计工作台和 D1-D4 产生的项目语义必须被 Step00-10 消费，不能停留在模板说明。
4. 防止假完成：结构门禁 success 不再等同于内容完整；必须增加语义覆盖、占位符边界和项目特异性评分。
5. 并行隔离：10 个项目并行运行时，合约、缓存、AI 补全、source refs、评分报告必须严格绑定当前 save/draft。

## 2. 对现有方案的判断

### 2.1 应采纳的内容

对方方案中有价值的点：

1. `Archetype 强推断` 是正确入口。当前退化为 `generic_playable` 后，所有下游都会被迫通用化。
2. `开放问题 OQ 专属化` 很重要。它能把缺失参数提前暴露，而不是等 Step08/09 生成空洞计划。
3. `决策专属内容生成` 是 Step02/03 的关键，能解决 action_01、REQ-001 这类无语义内容。
4. `资产专属内容填充` 是 Step04/09 的关键，能避免只生成 `asset_ui_placeholder`。
5. `美术风格验证` 是必要门禁，能阻止明显不匹配风格进入生产。
6. `程序任务语义化命名` 是 Step08/11 的关键，能让代码文件和任务标题反映项目内容。
7. `两项目对照实例` 很适合做回归验收样例。

### 2.2 必须修正的风险

对方方案如果直接实现，仍有几个风险：

1. 示例中有较多 Python 字典和硬编码映射，正式实现不能把游戏内容硬编码进业务代码。
2. Archetype、资产、任务、风格规则必须是数据驱动，放在 `knowledge/design_data/` 或 schema 管理的知识文件中。
3. 只改 Step00/01/04/07/08 不够，Step02/03/05/06/09/10 也必须同时接入语义闭环。
4. 如果没有统一的 Project DNA，多个优化点会各自读取 decisions，容易出现同一项目在不同步骤解释不一致。
5. 如果没有语义覆盖矩阵，Step10 仍可能把 placeholder 对齐误判为完整。
6. 如果不加并行上下文签名，模板缓存和 source fallback 仍可能在多项目并行时串档。

因此，融合方案采用：

```text
Project DNA 作为唯一项目语义根
Archetype Requirements 作为类型范式层
Open Questions 作为缺失参数补全层
Program Capability / Art Taxonomy 作为下游消费层
Semantic Coverage Matrix 作为门禁和评分层
```

## 3. 目标架构

### 3.1 语义链路

```text
设计工作台 / 模板 / AI 补全
  ↓
D4 handoff_manifest + decisions.json
  ↓
Step00 project_identity_contract
  ↓
Step01 archetype_requirements + open_questions
  ↓
Step02 project_dna_contract + playable_scenario_contract
  ↓
Step03 program_capability_contract
  ↓
Step04 art_taxonomy_contract + asset_strategy_matrix
  ↓
Step05/06 semantic review + customization_score_report
  ↓
Step07 style_fit_report
  ↓
Step08 project-specific program_plan_contract
  ↓
Step09 project-specific art_production_task_contract
  ↓
Step10 semantic_alignment_report
  ↓
Step11-14 real execution / art production / scene assembly / integration validation
```

### 3.2 三层内容模型

| 层级 | 作用 | 存放位置 |
|---|---|---|
| 通用标准层 | 所有游戏都必须具备的合约字段和验证规则 | `knowledge/schemas/ai_design/` |
| 类型范式层 | tower_defense、narrative_puzzle 等类型最低结构 | `knowledge/design_data/archetypes/` |
| 项目定制层 | 当前项目的实体、动作、资产、任务、验收 | 当前 save/draft 的 stage 产物 |

## 5. 新增或扩展核心模块

为避免继续把业务逻辑堆入 `core/engines/generation.py`，新增或扩展设计语义模块。原则是：优先扩展现有 `core/design/` 能力；只有当职责明显独立且现有文件不适合承载时，才新增 `core/design_semantics/`。

```text
core/design/
  requirements.py              # 扩展现有 archetype 检测和 requirements 输出
  project_dna.py               # 新增，Project DNA 构建
  open_questions.py            # 新增，OQ 生成和解析
  program_capabilities.py      # 新增，程序能力合约
  art_taxonomy.py              # 新增，美术分类和资产策略
  style_fit.py                 # 新增，风格兼容性校验
  semantic_coverage.py         # 新增，覆盖矩阵和评分
  semantic_alignment.py        # 新增，Step10 语义对齐
```

职责边界：

| 模块 | 职责 |
|---|---|
| `requirements.py` | 扩展现有 `detect_archetype()` 和 `build_archetype_requirements()`，读取 JSON 类型规则，保持旧调用兼容 |
| `project_dna.py` | 将 decisions/handoff/archetype/playable contracts 合成 Project DNA |
| `open_questions.py` | 按 archetype 生成项目专属 OQ，并将答案回写到 Project DNA |
| `program_capabilities.py` | 从 Project DNA 生成程序能力 |
| `art_taxonomy.py` | 从 Project DNA 生成美术分类和资产策略 |
| `style_fit.py` | 校验风格与 archetype/profile 是否匹配 |
| `semantic_coverage.py` | 计算项目语义覆盖、质量分、模板化比例、placeholder 比例 |
| `semantic_alignment.py` | Step10 语义对齐 |

与现有文件的分工：

| 现有文件 | 保留职责 | 本计划新增/扩展关系 |
|---|---|---|
| `core/design/requirements.py` | D3/D4 当前 archetype requirements 生成 | 直接扩展，不另造冲突 detector |
| `core/design/playable_contracts.py` | playable contracts 构建和冻结候选 | Project DNA 是上层语义根，可调用 playable contracts，不替代其职责 |
| `core/design/export_adapter.py` | 设计工作台导出 source artifacts | 继续负责导出；新增字段通过结构化 handoff 扩展 |
| `core/ai_design/contract_gate.py` | 既有合同门禁 | 新语义校验优先委托或复用，不重复写一套合同校验器 |

`generation.py` 只允许调用这些服务并写出结果，不新增复杂业务逻辑。

## 7. 步骤级开发方案

### 7.1 D1-D4：设计工作台与导出交接

开发内容：

1. 模板选择后记录 `template_id`、`template_hash`、`template_origin.reference_only`。
2. AI 补全内容写入 `provenance`，区分 `user_selected`、`template_seeded`、`ai_suggested`、`fallback_generated`。
3. D4 的 `handoff_manifest.json` 增加 `project_signature` 和 `decision_source_index`。
4. 禁止历史模板说明直接进入后续任务标题、文件名、资产 ID。

## 9. 并行隔离设计

必须支持 10 个项目并行运行。

### 9.1 项目签名

所有新增产物必须包含：

```json
{
  "draft_session_id": "...",
  "output_base_dir": "...",
  "linked_save_id": "... optional, only for archive binding",
  "project_id": "...",
  "project_signature": "..."
}
```

上下文加载遵循 deal/08 的决定：

```python
context = StructuredDesignContext.from_output_base(output_base_dir)
context = StructuredDesignContext.from_draft_session(draft_session_id, workspace_root)
```

`linked_save_id` 只能作为存档归属或 UI 展示信息，不能作为 D4/Step00-10 结构化上下文加载的唯一依据。

签名来源：

```text
hash(draft_session_id + output_base_dir + source_artifacts_path + decisions_hash + template_hash + project_name)
```

### 9.2 缓存隔离

以下缓存必须带签名：

1. archetype detection cache
2. template expansion cache
3. AI supplement cache
4. open question answer cache
5. semantic coverage cache

### 9.3 Source refs 校验

每个 stage 的 semantic validator 必须检查：

1. source refs 是否在当前 save/draft 下。
2. source refs 是否与当前 `project_signature` 一致。
3. 不允许“最近 draft fallback”覆盖当前项目显式 source。

## 13. 最终验收标准

### 13.1 通用验收

任意两个不同项目并行运行 Step00-10 后：

1. `project_identity_contract.project_signature` 不同。
2. `project_dna_contract` 不同。
3. Step03 程序能力不同。
4. Step04 资产分类不同。
5. Step08 程序任务不同。
6. Step09 美术任务不同。
7. Step10 对齐矩阵不同。
8. 质量分低于阈值时不能静默 success。

### 13.2 植物大战僵尸类项目最低验收

必须出现：

| 标准项 | 自动生成来源 |
|---|---|
| 车道/格子系统 | `archetype_requirements.required_systems[]` 包含 grid/lane；`program_capability_contract.capabilities[]` 包含 GridManager 或等价能力 |
| 阳光资源 | `project_dna_contract.resources[]` 包含 sun 或等价资源；`program_capability_contract.data_models[]` 绑定资源字段 |
| 植物放置动作 | `project_dna_contract.player_actions[]` 包含 place_plant/place_defense_unit；Step08 任务引用该 action |
| 敌人波次 | `project_dna_contract.objectives[]` 或 `core_entities[]` 包含 wave/enemy_wave；Step08 生成 WaveSpawn/EnemySpawn 任务 |
| 植物/敌人/阳光/HUD 资产 | `art_taxonomy_contract.asset_groups[]` 与 `asset_strategy_matrix.items[]` 覆盖 unit/resource/ui_hud |
| 波次胜负验收 | `project_dna_contract.acceptance_scenarios[]` 和 Step14 acceptance checks 覆盖 wave clear/fail |

### 13.3 请出示证件类项目最低验收

必须出现：

| 标准项 | 自动生成来源 |
|---|---|
| 证件数据模型 | `project_dna_contract.core_entities[]` 包含 document/passport；`program_capability_contract.data_models[]` 包含 document fields |
| 规则手册 | `project_dna_contract.core_entities[]` 或 `ui_surfaces[]` 包含 rulebook；Step08 生成 RuleBookManager 或等价任务 |
| 审查/批准/拒绝动作 | `project_dna_contract.player_actions[]` 包含 inspect/approve/reject；input contract 和 Step08 任务引用这些动作 |
| 扣分/罚款/日结 | `project_dna_contract.resources[]` 或 `objectives[]` 包含 penalty/fine/day_summary；program capabilities 绑定状态变化 |
| 检查台/证件/印章/规则书/UI 资产 | `art_taxonomy_contract.asset_groups[]` 与 `asset_strategy_matrix.items[]` 覆盖 desk/document/stamp/rulebook/ui |
| 审查配额和错误惩罚验收 | `project_dna_contract.acceptance_scenarios[]` 和 Step14 acceptance checks 覆盖 quota、wrong decision penalty |

## 14. 预期结果

完成后，系统不再只是“能生成一个 Unity 可见 Demo”，而是能从通用设计标准出发，为不同游戏生成具有独立内容的开发计划、美术计划和资源对齐结果。

Step00-10 的 success 将代表：

1. 项目身份明确。
2. 类型范式明确。
3. Project DNA 冻结。
4. 核心程序能力已生成。
5. 核心资产策略已生成。
6. 风格适配已验证。
7. 程序开发任务项目化。
8. 美术制作任务项目化。
9. 语义对齐真实通过。
10. 后续 Step11-14 有足够依据生成完整可玩流程。
